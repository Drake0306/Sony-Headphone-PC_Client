# Platform design conventions and technical UI constraints for a menu-bar / tray headphone-control app (macOS first, Windows second, Linux third) — as of 2026-11-07

Scope: facts a designer and developer need to make a menu-bar/tray presence plus a main/settings window feel native and current on macOS 26/27, Windows 11 (25H2/26H2), and (briefly) Linux, and to know which visual effects each UI stack can actually render. Every claim carries a URL; where a page could not be retrieved or a claim could not be verified it is listed under Gaps rather than asserted.

---

## Key Question 1 — macOS: current system design language (Liquid Glass in macOS 26 Tahoe; what changed in macOS 27 "Golden Gate")

### Takeaway
macOS 26 Tahoe (Sept 2025) introduced Liquid Glass, a translucent "functional layer" for controls/navigation that was widely criticised for legibility and the fully transparent menu bar; macOS 27 "Golden Gate" (announced WWDC June 2026, released 14 Sept 2026, Apple-silicon only) kept the language but walked back the most-disliked parts: a user-facing opacity slider, uniform and less-rounded window corners, edge-to-edge (non-floating) sidebars with coloured icons, and a uniform frosted toolbar. Design for "regular" glass in the control layer only, never in the content layer, and always test with Reduce Transparency / the opacity slider.

### Cited Findings
- macOS 27 "Golden Gate" was announced at WWDC in June 2026 and released 14 September 2026; point releases 27.0.1 (28 Sept), 27.2 (26 Oct), 27.3 public beta (5 Nov 2026). Requires Apple silicon (M1+); Tahoe is the last Intel release. — [MacRumors macOS 27 roundup](https://www.macrumors.com/roundup/macos-27/)
- macOS 27 adds a slider in System Settings > Appearance to set Liquid Glass translucency "from clear to a more opaque, tinted look"; overall glass opacity changed to diffuse complex backgrounds better, with "a darkened edge and brighter specular highlights" for depth. — [MacRumors](https://www.macrumors.com/roundup/macos-27/)
- macOS 27: all windows share one corner radius, "less rounded than in macOS Tahoe"; sidebars "no longer float. They extend edge-to-edge, and colored sidebar icons return"; apps get "uniform toolbars"; app icons gain more glass layers; squircle icon requirement retained. — [MacRumors](https://www.macrumors.com/roundup/macos-27/); corroborated by [Cult of Mac, 9 June 2026](https://www.cultofmac.com/news/liquid-glass-changes-ios-27-macos-27) (corner radius change "is automatic... also applies to third-party apps"; coloured sidebar icons only for the active app; toolbar "has a frosted look").
- Neither MacRumors nor Cult of Mac describe macOS 27 changes to the menu bar or Control Center specifically; the only menu-bar-related item is a 4 Nov 2026 report of Live Activities appearing in the Mac menu bar. — [MacRumors](https://www.macrumors.com/roundup/macos-27/); [Cult of Mac](https://www.cultofmac.com/news/liquid-glass-changes-ios-27-macos-27)
- Reception of Tahoe's Liquid Glass: AppleInsider's June 2025 review said the fully transparent menu bar "makes the top of the screen look like controls happened to line up there"; MacRumors headlined "Spotlight Shines, Liquid Glass Disappoints" (1 Aug 2025); MacStories' Viticci was more positive and noted Tahoe adds a dark gradient behind the bar for legibility and that wallpaper choice largely determines whether it works. — [AppleInsider](https://appleinsider.com/articles/25/06/20/macos-tahoe-review----glossy-changes-mask-genuine-improvements); [MacRumors](https://www.macrumors.com/2025/08/01/macos-tahoe-review); [MacStories](https://www.macstories.net/stories/macos-26-tahoe-the-macstories-review/2/)
- Tahoe fallback settings users may have on: System Settings > Menu Bar > "Show menu bar background", and Accessibility > Display > Reduce Transparency. — [OWC blog](https://eshop.macsales.com/blog/97650-blurry-or-beautiful-the-tweaks-and-tenets-of-apples-controversial-liquid-glass-design-in-macos-tahoe/)
- Apple HIG "Materials" (updated 9 Sept 2025): "Liquid Glass forms a distinct functional layer for controls and navigation elements — like tab bars and sidebars — that floats above the content layer." "Don't use Liquid Glass in the content layer." "Use Liquid Glass effects sparingly." Two variants: `regular` ("blurs and adjusts the luminosity of background content... Most system components use this variant... Use the regular variant... when components have a significant amount of text, such as alerts, sidebars, or popovers") and `clear` ("highly translucent... Use this variant for components that float above media backgrounds"; if the underlying content is bright, "consider adding a dark dimming layer of 35% opacity"). — [Apple HIG Materials](https://developer.apple.com/design/human-interface-guidelines/materials)
- HIG Materials, macOS: standard materials remain for the content layer via `NSVisualEffectView.Material`; two blending modes, "behind window and within window"; "Help ensure legibility by using vibrant colors on top of materials." — [Apple HIG Materials](https://developer.apple.com/design/human-interface-guidelines/materials)
- Apple "Adopting Liquid Glass": standard components ("bars, sheets, popovers, and controls") adopt the material automatically when built with the latest SDK; "Reduce your use of custom backgrounds in controls and navigation elements"; "Audit the backgrounds of sheets and popovers. Check whether you add a visual effect view to your popover's content view, and remove those custom background views"; custom glass via SwiftUI `glassEffect(_:in:)`, UIKit `UIGlassEffect`, AppKit `NSGlassEffectView`; combine custom glass shapes in a `GlassEffectContainer` for performance and morphing; button styles `.glass`, `.glassProminent`, AppKit `NSButton.BezelStyle.glass`; `backgroundExtensionEffect()` / `NSBackgroundExtensionView` to mirror content under sidebars; scroll edge effect via `scrollEdgeEffectStyle` / `safeAreaBar`; concentric shapes via `ConcentricRectangle` / `rect(corners:isUniform:)`; forms with `.grouped` style get the new metrics; section headers now render title-case; `UIDesignRequiresCompatibility` Info.plist key opts out of the new look when building with new SDKs. Sliders/toggles: "the knob transforms into Liquid Glass during interaction"; controls have an "extra-large size" option. — [Adopting Liquid Glass](https://developer.apple.com/documentation/technologyoverviews/adopting-liquid-glass)
- "people can choose a preferred look for Liquid Glass in their device's settings, or turn on accessibility settings that reduce transparency or motion... Ensure you test your app's custom elements, colors, and animations with different configurations of these settings." — [Adopting Liquid Glass](https://developer.apple.com/documentation/technologyoverviews/adopting-liquid-glass)
- Developer-forum report: a popover opened from a Liquid Glass container can keep either the glass toolbar or the button's morph effect, not both (thread 804141). — [Apple Developer Forums](https://developer.apple.com/forums/thread/804141)
- Apple's Tahoe window-resizing bug: macOS 26.3 release notes first claimed it fixed, then re-listed it as a "known issue". — [via search result summary of minifeed/Apple notes](https://minifeed.net/items/VkTzKavDYGV3)

### Inferences
- For a headphone popover, the HIG's own rule maps cleanly: the popover chrome and toolbar-like controls (mode segmented control, sliders) are "functional layer" and may use regular glass; the EQ graph, battery figures and device artwork are "content layer" and should sit on standard materials or solid backgrounds, not glass.
- Because users on both 26 and 27 can turn glass opaque (Reduce Transparency, or the 27 opacity slider), any design that depends on translucency for contrast or branding will break for a meaningful fraction of users; design the opaque state first.
- macOS 27's return to uniform, less-rounded corners and edge-to-edge sidebars means a Settings window built with `NavigationSplitView` + `.grouped` `Form` will automatically track the current look across 26→27; hand-built chrome will not.

### Gaps
- No source found describing specific macOS 27 changes to the menu bar, Control Center, or `MenuBarExtra` popover chrome; Apple's HIG "The menu bar" change log shows no entry after 9 June 2025.
- WWDC 2026 session numbers/titles on Liquid Glass were not retrieved (only press coverage of the keynote).
- The exact numeric corner radius macOS 27 uses for windows was not found in any source.

## Key Question 2 — macOS: HIG on menu bar extras, popovers, materials, SF Symbols, sidebars/settings windows

### Takeaway
The HIG is explicit: menu bar height is 24 pt, menu bar extra icons are black-and-clear template images (or SF Symbols), the default click behaviour should be a menu, not a popover ("unless the app functionality... is too complex for a menu"), and users must be able to remove the extra. Popovers should be "only big enough to display its contents", dismiss on outside click, show one at a time, and on macOS may be detachable. No official popover width number exists in the HIG.

### Cited Findings
- "A menu bar extra exposes app-specific functionality using an icon that appears in the menu bar when your app is running, even when it's not the frontmost app." "When necessary, the system hides menu bar extras to make room for app menus." — [Apple HIG, The menu bar](https://developer.apple.com/design/human-interface-guidelines/the-menu-bar)
- "Consider using a symbol to represent your menu bar extra. You can create an icon or you can choose one of the SF Symbols... Both interface icons and symbols use black and clear colors to define their shapes; the system can apply other colors to the black areas in each image so it looks good on both dark and light menu bars, and when your menu bar extra is selected. The menu bar's height is 24 pt." — [Apple HIG, The menu bar](https://developer.apple.com/design/human-interface-guidelines/the-menu-bar)
- "Display a menu — not a popover — when people click your menu bar extra. Unless the app functionality you want to expose is too complex for a menu, avoid presenting it in a popover." — [Apple HIG, The menu bar](https://developer.apple.com/design/human-interface-guidelines/the-menu-bar)
- "Let people — not your app — decide whether to put your menu bar extra in the menu bar... consider giving people the option of doing so during setup." "Avoid relying on the presence of menu bar extras." "Consider exposing app-specific functionality in other ways, too" (e.g. a Dock menu). HIG change log last entry: 9 June 2025; references WWDC 2025 session 208. — [Apple HIG, The menu bar](https://developer.apple.com/design/human-interface-guidelines/the-menu-bar)
- HIG app menu: "Settings…" item "Opens your settings window"; About item name "16 characters or fewer". — [Apple HIG, The menu bar](https://developer.apple.com/design/human-interface-guidelines/the-menu-bar)
- Popovers: "Use a popover to expose a small amount of information or functionality." "Make a popover only big enough to display its contents and point to the place it came from." "Show one popover at a time." A popover "generally closes when people click or tap outside it or select an item within it." "Always save work when automatically closing a nonmodal popover." If a popover switches between condensed/expanded views, "animate the change to avoid giving the impression that a new popover replaced the old one." macOS-only: "Consider letting people detach a popover" (it becomes a panel when dragged) and "Make minimal appearance changes to a detached popover." — [Apple HIG, Popovers](https://developer.apple.com/design/human-interface-guidelines/popovers)
- Materials/vibrancy: see KQ1 findings (regular vs clear glass, NSVisualEffectView materials, vibrant colours). — [Apple HIG Materials](https://developer.apple.com/design/human-interface-guidelines/materials)
- Sidebars in macOS 27 extend edge-to-edge with coloured icons; Apple recommends `NavigationSplitView` / `NSSplitViewController` and `inspector(isPresented:)` for sidebar+inspector layouts, and `.grouped` form style for settings-like forms. — [Adopting Liquid Glass](https://developer.apple.com/documentation/technologyoverviews/adopting-liquid-glass); [MacRumors](https://www.macrumors.com/roundup/macos-27/)
- Standard icons: Apple asks apps to "Adopt standard icons in menu items" and to "Provide an accessibility label for every icon." — [Adopting Liquid Glass](https://developer.apple.com/documentation/technologyoverviews/adopting-liquid-glass)
- An older third-party article notes Apple's HIG "doesn't contain much information related to designing menu bar extras" — still true of the current page beyond the bullets above. — [Indie Stack, April 2022](https://indiestack.com/2022/04/)

### Inferences
- A headphone app with ANC/ambient slider, ULT toggle, battery, EQ and multipoint is plausibly "too complex for a menu", which is the HIG's stated exception; but the app should still offer a plain-menu path (e.g. right-click or Option-click) and a Settings toggle to hide the extra.
- Template icon: supply a 1x/2x black-on-clear PDF/PNG or an SF Symbol sized for the 24 pt bar (Electron and Tauri community docs converge on ~16–22 pt artwork; see KQ4).
- Popover width: no Apple number; Apple's own Control Center modules and third-party guidance (Tauri guide uses 360 px) cluster around 300–380 pt. Treat 320–360 pt as a defensible default.

### Gaps
- The HIG popovers page has no explicit width/height guidance and no material-specific guidance; no official "Control Center module" HIG page was found.
- No HIG page for SF Symbols in menu bar extras was fetched beyond the sentence quoted above (SF Symbols HIG page not retrieved).

## Key Question 3 — SwiftUI `MenuBarExtra`: window vs menu style, sizing, animation, limitations and workarounds (custom NSPanel, dismissal, Dock icon, launch at login, Settings)

### Takeaway
`MenuBarExtra` (macOS 13+) offers `.menu` (pull-down NSMenu) and `.window` ("popover-like window") styles but exposes no API for presentation state, the `NSStatusItem`, or the window; sizing is derived from content ideal size and has recurring bugs on Tahoe; the community standard is either the `MenuBarExtraAccess` package or replacing it with `NSStatusItem` + non-activating `NSPanel` + `NSHostingController`. Opening a Settings window from an accessory (no-Dock-icon) app needs the activation-policy dance. Launch at login is `SMAppService.mainApp` (macOS 13+).

### Cited Findings
- `MenuBarExtraStyle` (macOS 13.0+): `.menu` "renders its contents as a menu that pulls down from the icon"; `.window` "renders its contents in a popover-like window"; `.automatic` default. — [Apple Developer Docs, MenuBarExtraStyle](https://developer.apple.com/documentation/swiftui/menubarextrastyle)
- "There is no 1st-party MenuBarExtra API to obtain or set the menu presentation state, access the status item, or access the popup's NSWindow." `MenuBarExtraAccess` adds `.menuBarExtraAccess(isPresented:isEnabled:) { statusItem in }` and `.introspectMenuBarExtraWindow { window in }` (window style only), macOS 13+, no private API ("App Store safe"). Known issue with `.menu` style: SwiftUI blocks the run loop while the menu is open, so `isPresented` observation and programmatic dismissal do not work. The status item "can occasionally get out of sync" and invert state. — [MenuBarExtraAccess README](https://github.com/orchetect/MenuBarExtraAccess)
- One app locates the SwiftUI popup by style mask ("NSPanel + .nonactivatingPanel"), described as "stable across SwiftUI versions". — [scrobblr v0.1.10 release notes](https://github.com/asharahmed/scrobblr/releases/tag/v0.1.10)
- `FluidMenuBarExtra` is a drop-in replacement that adds animated resizing when content changes and exposes scene phase. — [Swift Package Registry: FluidMenuBarExtra](https://swiftpackageregistry.com/wadetregaskis/FluidMenuBarExtra)
- Sizing bug: `MenuBarExtra(style: .window)` sizes its window from the content's ideal size; an inner `ScrollView` reports ideal height 0; workaround is a fixed height (observed on macOS 26.4). — [mac-app-for-claude-code v0.1.1 notes](https://github.com/anhyobin/mac-app-for-claude-code/releases/tag/v0.1.1)
- Older forum thread: window-style content lays out correctly the first time but "from the second time on, the view resizes to a certain smaller height"; switching to `.menu` avoided it. — [Apple Developer Forums thread 741553](https://developer.apple.com/forums/thread/741553)
- Forum thread 802313: hover/layout issue in a MenuBarExtra with ScrollView+LazyVStack on Tahoe; reported fixed "after the update to macOS 26.1 and Xcode 26.1"; disabling Liquid Glass via Info.plist also changed behaviour. — [Apple Developer Forums thread 802313](https://developer.apple.com/forums/thread/802313)
- One project replaced `MenuBarExtra` with "an AppKit shell (NSStatusItem + NSPanel + NSHostingController)" to fix "a macOS 26 layout-cycle crash". — [fosrl/apple PR 43](https://github.com/fosrl/apple/pull/43)
- `MenuBarKit` package: `MenuBarPanel` is "a borderless, non-activating floating NSPanel that presents popover-style content without anchoring to a view", survives Ice hiding the status icon; requires macOS 26, uses Liquid Glass. — [MenuBarKit](https://github.com/gabriarceus/MenuBarKit)
- Settings from a menu-bar app: `SettingsLink` is unreliable; apps with `.accessory` activation policy (no Dock icon) open windows behind other apps. History: `showPreferencesWindow:` (≤12), `showSettingsWindow:` (13), selector broke on 14; `openSettings` environment action works on 15 but author reports it does not work on Tahoe (26). Workaround: hidden off-screen `Window` scene declared *before* the `Settings` scene; on request, `NSApp.setActivationPolicy(.regular)`, `NSApp.activate(ignoringOtherApps: true)`, call `openSettings()`, then after a short delay `makeKeyAndOrderFront(nil)` / `orderFrontRegardless()`; restore `.accessory` when the Settings window closes. — [steipete.me, 2025](https://steipete.me/posts/2025/showing-settings-from-macos-menu-bar-items/)
- Launch at login: `SMAppService.mainApp` ("An app service object for the main application as a login item"), macOS 13+. — [Apple Developer Docs](https://developer.apple.com/documentation/servicemanagement/smappservice/mainapp); usage pattern `register()`/`unregister()` from a toggle, and "it's important to read the status from SMAppService rather than storing this setting locally in the app" because users can remove it in System Settings. — [Nil Coalescing](https://nilcoalescing.com/blog/LaunchAtLoginSetting)
- Ice (menu bar manager) is written in Swift; a fork, Thaw, exists to keep it compatible with newer macOS. — [Ice mirror](https://github.com/farhadfa22/Ice); [Thaw](https://sourceforge.net/projects/thaw.mirror/)

### Inferences
- For a "cool, animated" popover with sliders and an EQ, the safest 2026 architecture on macOS is AppKit-hosted: `NSStatusItem` + non-activating `NSPanel` (`.nonactivatingPanel`, borderless) + `NSHostingController`, which gives full control over size animation, dismissal on focus loss (`resignKey`/global click monitor), and Liquid Glass via `NSGlassEffectView` or SwiftUI `glassEffect`; keep `MenuBarExtra(.menu)` only as a lightweight fallback.
- If staying with `MenuBarExtra(.window)`, pin a fixed frame on the root view and avoid relying on `ScrollView` ideal sizing; add `MenuBarExtraAccess` for programmatic show/hide.
- Dock icon: use `LSUIElement`/`.accessory` and expect to temporarily switch to `.regular` whenever a real window (Settings, EQ editor) must come to front.

### Gaps
- No Apple documentation retrieved on `MenuBarExtra` window-style animation support (none appears to exist); animation claims rest on third-party packages.
- Whether the `openSettings` regression on Tahoe was fixed in 26.x or 27 could not be verified.
- Apple's `SMAppService` page body was not fetched beyond the summary line; notarization implications for login items were not found.

## Key Question 4 — Apple's own AirPods controls (the reference users compare against)

### Takeaway
On macOS, AirPods controls live inside the Sound item of Control Center / the menu bar: expanding the AirPods entry reveals Noise Control (Off / Transparency / Adaptive / Noise Cancellation) and other per-model options; a dedicated AirPods menu bar item can be enabled via Control Center settings. Apple's current (macOS 27) Mac Help page routes full configuration through System Settings > [AirPods name]. I could not retrieve a primary Apple screenshot or spec of the Control Center module layout.

### Cited Findings
- Apple Mac Help (macOS 13 guide): choose Noise Cancellation, Transparency, or Off "from the menu bar or Control Center Sound control"; AirPods must be connected and in-ear for all options to appear; you can add the AirPods icon or Sound control to the menu bar via Control Center settings ("Always Show in Menu Bar"). — [Apple Support (en-nz, macOS 13)](https://support.apple.com/en-nz/guide/mac-help/mchld2f124d1/13/mac)
- Apple Mac Help current page (path "/27/", includes "What's new in macOS 27"): configure AirPods from System Settings > click AirPods name in sidebar; "Options vary by model"; links to AirPods User Guide for Noise Control and Spatial Audio; mentions adding the Bluetooth or Sound status menu to the menu bar. Does not describe the Control Center module. — [Apple Support (en-gb, current)](https://support.apple.com/en-gb/guide/mac-help/mchld2f124d1/mac)
- A 2025-era walkthrough: "open Control Center, click Sound, expand your AirPods, and click Adaptive under Noise Control." — [SwitchingToMac](https://www.switchingtomac.com/set-up-airpods-pro-adaptive-audio/); MacRumors how-to covers the same path. — [MacRumors](https://www.macrumors.com/how-to/control-noise-cancellation-airpods-pro/)
- The Raycast "AirPods Noise Control" extension notes Control Center "does not expose the name of the output devices in the Sound menu"; it scripts by list position — i.e. the module is not automatable by name. — [Raycast store](https://www.raycast.com/chrahe/airpods-noise-control)
- NoiseBuddy (insidegui) — a third-party menu-bar noise-control app — "doesn't work in recent versions of macOS"; similar functionality moved into AirBuddy. — [NoiseBuddy GitHub](https://github.com/insidegui/NoiseBuddy)
- OWC guide to customising AirPods audio in macOS Sequoia (settings location). — [OWC](https://eshop.macsales.com/blog/96592-how-to-fully-customize-airpods-audio-in-macos-sequoia/)

### Inferences
- The native reference is a compact, text-first list inside a ~300–350 pt-wide Control Center panel: device name, volume slider, then a Noise Control row of 3–4 equal-width segmented glass buttons with SF Symbol icons and labels, plus spatial audio toggles. A Sony app that mirrors "device header → volume → Noise Control segmented row → extras" will read as native.
- Battery for AirPods is shown in the Bluetooth menu bar item / Control Center Bluetooth module (per-bud and case percentages) rather than in the Sound module — unverified for current macOS, see Gaps.

### Gaps
- No primary Apple source (HIG or support page with screenshot) describing the exact layout, widths, or control types of the AirPods section in Control Center on macOS 26/27 was retrievable; the structure above is reconstructed from how-to articles.
- Battery display location for AirPods on macOS 27 not verified.

## Key Question 5 — Windows 11: current Fluent design, materials, corner radii, typography, taskbar flyouts, and tray flyout requirements

### Takeaway
Windows 11 Fluent as of late 2026 still rests on Mica (opaque, wallpaper-tinted, for app base layers) and Acrylic (translucent, "used only for transient, light-dismiss surfaces such as flyouts and context menus"), 8 px corners for windows/flyouts and 4 px for controls, and Segoe UI Variable (Body 14/20, Caption 12/16). The official Win32 tray guidance is: right-click → context menu, left-click → "a popup window, a dialog box or the program window itself" placed near the click (`CalculatePopupWindowPosition`), with the user able to remove the icon. Windows 11 26H2 (rolling out Oct–Nov 2026) adds taskbar repositioning and a smaller taskbar; Quick Settings is being reworked for speed and gains a dark-mode toggle (Insider-only, ViVeTool).

### Cited Findings
- "Mica is an opaque material that incorporates the user's theme and desktop wallpaper... only captures the background wallpaper once... recommend it for the foundation layer of your app, especially in the title bar area." "Acrylic is a semi-transparent material that replicates the effect of frosted glass. It's used only for transient, light-dismiss surfaces such as flyouts and context menus." — [Microsoft Learn, System backdrops (updated 19 Aug 2026)](https://learn.microsoft.com/en-us/windows/apps/develop/ui/system-backdrops)
- WinUI 3 APIs: `Window.SystemBackdrop` = `MicaBackdrop` (`Kind="BaseAlt"` for Mica Alt) or `DesktopAcrylicBackdrop`; `FlyoutBase.SystemBackdrop`, `Popup.SystemBackdrop`, `MenuFlyoutPresenter.SystemBackdrop` accept `DesktopAcrylicBackdrop`; `SystemBackdropElement` (requires Windows App SDK 2.0+) renders a backdrop inside any bounded element with `CornerRadius`; controllers `MicaController` / `DesktopAcrylicController` (`DesktopAcrylicKind.Thin`/`Base`) with `IsSupported()`, `SystemBackdropConfiguration.IsInputActive` and `.Theme`, and `TintColor`/`TintOpacity`/`LuminosityOpacity`/`FallbackColor`. Backdrops react to light/dark by default; after customising tint properties you must update them on theme change yourself. — [Microsoft Learn, System backdrops](https://learn.microsoft.com/en-us/windows/apps/develop/ui/system-backdrops)
- Geometry: "Top-level containers such as app windows, flyouts and dialogs are rounded using an 8px corner radius"; "In-page elements such as buttons and list backplates... 4px"; tooltips 4 px; bars (ProgressBar, ScrollBar, Slider) 4 px; no rounding where a flyout touches its invoker; globals `ControlCornerRadius` (4) and `OverlayCornerRadius` (8); Win32 apps opt in via DWM. — [Microsoft Learn, Geometry in Windows 11](https://learn.microsoft.com/en-us/windows/apps/design/signature-experiences/geometry)
- Typography: Windows ramp uses Segoe UI Variable; Caption 12/16, Body 14/20, Body Strong (semibold) 14/20, Body Large 18/24; Microsoft Learn names them "Small 12/16 epx" and "Text 14/20 epx"; "use Semibold rather than Bold for emphasis". — [Fluent 2 typography](https://fluent2.microsoft.design/typography); [Microsoft Learn, Typography in Windows 11](https://learn.microsoft.com/en-us/windows/apps/design/signature-experiences/typography)
- Notification area (tray) guidance (Win32, updated 15 Apr 2025): provide 16×16 and 32×32 icons and load with `LoadIconMetric`; "When a user right-clicks the icon, it should bring up a normal shortcut menu. However, the result of a single click with the left mouse button will vary... a popup window, a dialog box or the program window itself. For instance, it could show... a slider for the volume control." "The placement of a popup window or dialog box that results from the click should be placed near the coordinate of the click in the notification area. Use the CalculatePopupWindowPosition"; icon bounds via `Shell_NotifyIconGetRect`; use `NOTIFYICON_VERSION_4` and a registry GUID; "The user should have the final say on which icons they want to see... should also be given the option (normally through its shortcut menu) to remove the icon"; new icons go to the overflow area by default and only the user can promote them. — [Microsoft Learn, Notifications and the Notification Area](https://learn.microsoft.com/en-us/windows/win32/shell/notification-area)
- Windows 11 26H2 reached Release Preview as build 26300.9278 and began rolling out via Windows Update to 24H2/25H2 PCs (reports late Oct/early Nov 2026); headline changes: taskbar can be moved to top/left/right/bottom and a smaller taskbar size; Start/Search redesign. — [Digital Citizen](https://www.digitalcitizen.life/windows-11-26h2-reaches-release-preview-with-taskbar-and-search-changes/); [Pureinfotech](https://pureinfotech.com/windows-11-26h2-taskbar-move-resize/); [Windows Central](https://www.windowscentral.com/microsoft/windows-11/windows-11-2026-update-26h2-changes-for-start-menu-taskbar-and-search)
- Quick Settings: Microsoft told Windows Latest (April 2026) it is testing a faster-loading Quick Settings; 26H2 preview builds add a light/dark toggle in the flyout and restore button customisation, hidden behind ViVeTool. Microsoft said in April 2026 it is "finally focusing on Windows 11's design". — [Windows Latest, 9 Apr 2026](https://www.windowslatest.com/2026/04/09/microsoft-confirms-windows-11s-quick-settings-and-right-click-menu-will-load-faster); [Pureinfotech](https://pureinfotech.com/windows-11-26h2-quick-settings-dark-mode-toggle/); [Windows Latest, 6 Apr 2026](https://www.windowslatest.com/2026/04/06/microsoft-says-its-finally-focusing-on-windows-11s-design-starting-with-settings-control-panels-replacement)
- Historical: build 22533 (2022) redesigned the volume/brightness flyouts to Windows 11 style. — [XDA](https://www.xda-developers.com/new-windows-11-preview-finally-redesigns-the-volume-and-brightness-flyouts/)

## Key Question 6 — Building a Windows tray flyout: WinUI 3, WPF, or cross-platform; which effects each can render

### Takeaway
WinUI 3 has no first-party tray icon (the WinUI proposal was parked for "too much inconsistency with flyout, menu styles"); the de facto option is `H.NotifyIcon.WinUI` (NuGet, last versions 2024) with its `TrayPopup`, paired with `Window.SystemBackdrop`/`FlyoutBase.SystemBackdrop` for Mica/Acrylic. WPF (EarTrumpet, ModernFlyouts) can host a tray icon natively and apply Mica/Acrylic via DWM interop. Cross-platform stacks get Mica/Acrylic through DWM attributes (Tauri `window-vibrancy`, Flutter `flutter_acrylic`, Electron `backgroundMaterial`) with Windows 11 22H2+ requirements and known performance caveats on Win10.

### Cited Findings
- `H.NotifyIcon` is "an implementation of a NotifyIcon (aka system tray icon or taskbar icon) for the WinUI platform" (`H.NotifyIcon.WinUI` package) with notifications, context menus, `ICommand` support, Efficiency Mode, dynamic icon generation, and a `TrayPopup` / `PopupActivation` property; newest versions found date from 2024 (2.1.3, Aug 2024). — [H.NotifyIcon GitHub](https://www.github.com/HavenDV/H.NotifyIcon); [NuGet 2.0.34](https://www.nuget.org/packages/H.NotifyIcon/2.0.34)
- Microsoft's WinUI tray-icon proposal (microsoft-ui-xaml issue 2020) noted "too much inconsistency with flyout, menu styles at present" — not a shipped API. — [microsoft-ui-xaml issue 2020](https://www.github.com/microsoft/microsoft-ui-xaml/issues/2020)
- Windows backdrop controller docs for Win32/other frameworks. — [Microsoft Learn, system backdrop controller](https://learn.microsoft.com/windows/apps/windows-app-sdk/system-backdrop-controller)
- Tauri `window-vibrancy`: Windows `apply_blur` (Win7/10/11 22H1 only; poor performance when resizing/dragging on Win11 22621+), `apply_acrylic` (Win10/11; poor performance on Win10 1903+ and Win11 22000), `apply_mica` (Win11 only; uses `DwmSetWindowAttribute` DWMSBT_MAINWINDOW on 22523+, undocumented `DWMWA_MICA_EFFECT` on 22000); Linux unsupported ("depend on the end user's compositor"). Requires `"transparent": true` and transparent `html, body`. — [window-vibrancy README](https://github.com/tauri-apps/window-vibrancy); [tauri vibrancy/windows.rs](https://docs.rs/crate/tauri/2.1.1/source/src/vibrancy/windows.rs)
- Flutter `flutter_acrylic` 1.1.4 (published ~2 years ago): Windows effects transparent/disabled/solid/aero/acrylic/mica/tabbed; acrylic needs Win10 1803+, mica Win11, tabbed Win11 22523+; on Win10 acrylic "causes lag when dragging the window" and blur "can also leak outside the window boundary", so a custom frame (bitsdojo_window) is often needed. — [pub.dev flutter_acrylic](https://pub.dev/packages/flutter_acrylic)
- Electron: `win.setBackgroundMaterial(material)` with `auto|none|mica|acrylic|tabbed`, "only supported on Windows 11 22H2 and up"; `vibe` README: "there is a way to have titlebar-less framed Mica windows, it does not work with Electron, and would unfortunately require changes in Electron's internals"; set `nativeTheme.themeSource` to force acrylic theme; a community gist reports "Electron v25 mica not active on frameless window". — [Electron BrowserWindow docs](https://www.electronjs.org/docs/latest/api/browser-window); [pykeio/vibe](https://github.com/pykeio/vibe); [gist](https://gist.github.com/34cf667b21a5075d1f6fbe093d7ad7f9)

### Inferences
- Native WinUI 3 + H.NotifyIcon yields the most faithful Fluent flyout (true Acrylic on a `Popup`/`Flyout`, 8 px corners, Segoe UI Variable, light-dismiss for free) at the cost of a Windows-only codebase and a third-party tray dependency that has been quiet since 2024.
- For cross-platform stacks, plan on an opaque fallback: Mica/Acrylic availability depends on Win11 22H2+, user transparency settings, and (for Electron) frameless-window quirks.

### Gaps
- No current (2025–2026) verification that H.NotifyIcon works with Windows App SDK 1.7/2.0.
- ModernFlyouts and Files app implementation details were not retrieved.
- WPF-specific Mica/Acrylic how-to (DWM interop) not fetched.

## Key Question 7 — Cross-platform stacks for a native-feeling menu-bar/tray app: capability matrix

### Takeaway
Tauri 2 is the strongest cross-platform option for a small, animated, translucent menu-bar/tray app (tray + positioner plugin + `window-vibrancy` incl. `apply_liquid_glass` on macOS 26+, ~10–26 MB binaries, web animation libraries); Electron matches its effects with a far larger footprint; Flutter has tray and acrylic plugins of mixed maintenance; Avalonia, Qt, Compose Multiplatform and Slint all have documented tray APIs but weaker/undocumented translucency stories; SwiftUI/AppKit on macOS and WinUI 3 on Windows remain the only stacks that get Liquid Glass / Acrylic exactly as the OS draws them.

### Cited Findings
- **Tauri 2** — tray via `TrayIconBuilder` (`icon_as_template(true)`, `show_menu_on_left_click(false)`), positioner plugin `Position::TrayCenter` (needs `tray-icon` feature and forwarding `tauri_plugin_positioner::on_tray_event`, otherwise the window appears top-left), window config `decorations:false, transparent:true, alwaysOnTop:true, visible:false, skipTaskbar:true`, `macOSPrivateApi:true` for vibrancy; hide on `Focused(false)` plus `app.hide()` on macOS; `apply_vibrancy(&window, NSVisualEffectMaterial::HudWindow, None, Some(18.0))` (18 pt corner radius); recommended tray PNG 22×22 white-on-transparent; autostart via `tauri-plugin-autostart` (`MacosLauncher::LaunchAgent`, appears in Login Items); author claims binary < 10 MB. — [DEV: Complete guide to a macOS menu bar app with Tauri v2](https://dev.to/hiyoyok/complete-guide-to-building-a-macos-menu-bar-app-with-tauri-v2-aji)
- `window-vibrancy` macOS: `apply_vibrancy`/`clear_vibrancy` (10.10+), `apply_liquid_glass`/`clear_liquid_glass` (macOS 26+, custom radius, tint, opacity, `interactive` — `interactive(true)` requires macOS 27+ and is silently ignored on 26); WebView reparenting via `.content_view()`. — [window-vibrancy README](https://github.com/tauri-apps/window-vibrancy)
- Size/memory: one benchmark 8.6 MB (Tauri 2) vs 244 MB (Electron) installer, 172 MB vs 409 MB RAM with six windows; a June 2026 census of ~26,000 shipped macOS/Windows apps found Tauri apps average 26.2 MB vs 406.9 MB for Electron; a 2026 guide gives Electron 80–200 MB bundle / 200–400 MB idle RAM vs Tauri 2–40 MB / 30–80 MB (rough). — [youngju.dev deep dive, 14 May 2026](https://www.youngju.dev/blog/culture/2026-05-14-tauri-2-rust-webview-desktop-mobile-electron-alternative-deep-dive-2026.en); [Desktop Insights, State of desktop runtimes 2026](https://desktopinsights.com/blog/state-of-desktop-app-runtimes-2026); [pkgpulse Electron vs Tauri 2026](https://www.pkgpulse.com/guides/electron-vs-tauri-2026)
- **Electron** — `Tray` API: macOS icons must be Template Images (filename ends in "Template", 16×16 @72 dpi + 32×32 @2x), Windows prefers `.ico` and a GUID "only with code-signed executables", Linux uses StatusNotifierItem with `GtkStatusIcon` fallback; `click` event carries `bounds`/`position` (on Linux "the StatusNotifierItem spec does not specify which action would cause an activation"); `getBounds()` on macOS/Windows; `mouse-up` not emitted on macOS when a context menu is set; no built-in popover anchoring. `setVibrancy` types: titlebar, selection, menu, popover, sidebar, header, sheet, window, hud, fullscreen-ui, tooltip, content, under-window, under-page; `animationDuration` only for fade in/out. — [Electron Tray docs](https://www.electronjs.org/docs/latest/api/tray); [Electron BrowserWindow docs](https://www.electronjs.org/docs/latest/api/browser-window)
- **Flutter** — `tray_manager` rated well-maintained, `system_tray` poor, `desktop_tray` 2026.4.19 (unverified publisher); `flutter_acrylic` 1.1.4: macOS materials titlebar, menu, popover, sidebar, headerView, sheet, windowBackground, hudWindow, fullScreenUI, toolTip, contentBackground, underWindowBackground, underPageBackground; macOS 10.14.6+; Linux blur depends on compositor. — [fluttergems Windows list (updated 1 Apr 2026)](https://fluttergems.dev/windows/); [pub.dev desktop_tray](https://pub.dev/packages/desktop_tray/install); [pub.dev flutter_acrylic](https://pub.dev/packages/flutter_acrylic)
- **Avalonia** — built-in `TrayIcon` (Icon, ToolTipText, `NativeMenu`, `Command`, `IsVisible`, multiple icons) declared at `Application` level; Windows: right-click menu / left-click Command; macOS: click opens menu; Linux needs StatusNotifierItem/AppIndicator (GNOME may need the extension). Avalonia `Menu` control not supported in tray. — [Avalonia docs, TrayIcon](https://docs.avaloniaui.net/docs/reference/controls/tray-icon)
- **Qt 6** — `QSystemTrayIcon` on Windows, macOS, and Linux (D-Bus StatusNotifierItem: KDE, GNOME, Xfce, LXQt, DDE; or XEmbed); `ActivationReason` Trigger/Context/DoubleClick/MiddleClick; `isSystemTrayAvailable()`; "GNOME Shell since 3.26 does not support all activation reasons without shell extensions"; on macOS DoubleClick "will only be emitted if no context menu is set, since the menu opens on mouse press". — [Qt 6 QSystemTrayIcon](https://doc.qt.io/qt-6/qsystemtrayicon.html)
- **Compose Multiplatform** — desktop `Tray` composable: "you can use the Tray composable to send notifications... you can also add an application icon to the system tray". — [JetBrains docs](https://jetbrains.com/help/kotlin-multiplatform-dev/compose-desktop-components.html)
- **Slint** — `SystemTrayIcon` element (icon, tooltip, menu); Linux requires a StatusNotifierItem implementation ("plain X11 system trays are not supported"); tray support was listed as upcoming in Slint's 9 Oct 2025 "desktop-ready" post and is now documented. — [Slint docs, SystemTrayIcon](https://docs.slint.dev/latest/docs/slint/reference/window/systemtrayicon/); [Slint blog, 9 Oct 2025](https://slint.dev/blog/making-slint-desktop-ready)
- **Native SwiftUI/AppKit** — see KQ1/KQ3: `glassEffect`, `GlassEffectContainer`, `NSGlassEffectView`, `NSVisualEffectView`, `NSStatusItem`, `NSPanel`. — [Adopting Liquid Glass](https://developer.apple.com/documentation/technologyoverviews/adopting-liquid-glass)
- A skills-guide caution: don't treat "macOS vibrancy, Liquid Glass, Windows Mica, and Acrylic as interchangeable"; provide an opaque fallback. — [add-tauri-native-window-effects skill](https://claudskills.com/skills/add-tauri-native-window-effects/SKILL.md)
- Translucent sidebars in Electron: popover vibrancy is stronger than sidebar vibrancy on macOS. — [engineered.at](https://engineered.at/articles/translucent-sidebars-in-electron-apps)

### Inferences
- For "cool, interactive, animated": Tauri 2 + a web animation library (Framer Motion/Motion, GSAP, CSS spring animations) gives the most design freedom with the smallest cross-platform footprint, and can layer real Liquid Glass (macOS 26+/27 `interactive`) or Mica/Acrylic under the webview; its weaknesses are platform-webview inconsistency (WebKit vs WebView2 rendering, fonts) and that controls are not the OS's own (no system slider knob morph, no native `NSMenu`).
- Native SwiftUI (macOS) + WinUI 3 (Windows) is the only path to pixel-exact system materials and control behaviours (glass knob morph, scroll edge effects, Acrylic flyouts); it doubles the UI code and loses Linux unless a third stack is added.
- Avalonia/Qt/Compose/Slint are viable for the tray icon itself, but none has a documented first-party Liquid Glass or Mica story in the sources found; they fit a utility look, not a glassy one.
- Binary-size ordering from the sources: Tauri (≈10–26 MB) < Flutter (≈40–80 MB, single agency claim) < Electron (≈80–400 MB).

### Gaps
- .NET MAUI was not researched (no results fetched); treat its tray/translucency support as unknown.
- No source found for Qt/QML, Avalonia, Compose, or Slint translucency (Mica/Acrylic/vibrancy) support; Avalonia's `TransparencyLevelHint` and Qt's `WA_TranslucentBackground` are known APIs but were not verified here.
- No authoritative list of "notable 2025–2026 apps" per stack was retrieved beyond the Tauri/Electron census aggregate; Raycast, Loop, Klack, AlDente, MonitorControl, Latest, Maccy, Stats implementation details were not fetched (only Ice/Thaw/MenuBarKit).
- Electron `visualEffectState` and `roundedCorners` option details were in the unread tail of the docs page.

## Key Question 8 — Linux: GNOME (libadwaita) and KDE (Plasma) expectations for tray / quick-settings integration

### Takeaway
Target the D-Bus StatusNotifierItem (SNI) protocol: KDE Plasma supports it natively via `KStatusNotifierItem` and prefers it; GNOME Shell has no built-in tray and needs the Ubuntu-maintained AppIndicator/KStatusNotifierItem extension (or the newer "Status Tray" extension), so a GNOME app cannot rely on a tray icon and should also expose its controls from the main window.

### Cited Findings
- KDE `KStatusNotifierItem` (KF6) implements the StatusNotifierItem D-Bus spec; it "provides an icon similar to the classical systemtray icons, with some key differences," notably attention/needs-attention state; some tray implementations "do not support passing icons by pixmap and will show a blank icon instead" — ship named theme icons. — [KDE API, KStatusNotifierItem](https://api.kde.org/kstatusnotifieritem.html)
- `libsystemtray`: a pure C++ SNI implementation for apps that don't depend on Qt or GTK (KDE developer Marco Martin's blog). — [notmart.org](https://notmart.org/blog/?p=6357)
- GNOME: the Ubuntu `gnome-shell-extension-appindicator` "integrates Ubuntu AppIndicators and KStatusNotifierItems (KDE's blessed successor of the systray) and legacy tray icons into GNOME Shell"; users should install it from extensions.gnome.org; maintainers say it "is not completely bug free and will probably never be"; last recorded push 6 May 2025. — [ubuntu/gnome-shell-extension-appindicator](https://github.com/ubuntu/gnome-Shell-extension-appindicator)
- "Status Tray" is a newer GNOME Shell extension that "brings back the system tray for applications using StatusNotifierItem (AppIndicator/SNI) protocol". — [keithvassallomt/status-tray](https://github.com/keithvassallomt/status-tray)
- Qt docs: "GNOME Shell since 3.26 does not support all activation reasons without shell extensions"; tooltip and wheel events only on X11. — [Qt 6 QSystemTrayIcon](https://doc.qt.io/qt-6/qsystemtrayicon.html)
- Slint and Avalonia both require SNI/AppIndicator on Linux; plain X11 trays unsupported in Slint. — [Slint docs](https://docs.slint.dev/latest/docs/slint/reference/window/systemtrayicon/); [Avalonia docs](https://docs.avaloniaui.net/docs/reference/controls/tray-icon)
- Window blur on Linux is compositor-dependent (KWin + kwin-forceblur, compiz, wayfire); no official backdrop API. — [pub.dev flutter_acrylic](https://pub.dev/packages/flutter_acrylic); [window-vibrancy README](https://github.com/tauri-apps/window-vibrancy)

### Inferences
- On Linux, design the "flyout" as an ordinary small top-level window (opaque, libadwaita/Breeze-neutral styling) opened from the SNI icon's activate signal, and keep a full main window as the primary surface; don't attempt translucency.

### Gaps
- No official GNOME HIG/libadwaita statement on status icons was found for 2025–2026; the "no built-in tray" position is inferred from the existence and necessity of the extensions.
- No KDE HIG page on Plasma quick-settings/applet integration (e.g. a Plasma applet vs an SNI icon) was retrieved.

## Key Question 9 — Accessibility and polish conventions: dark/light, reduced motion, keyboard navigation, native fonts, popover sizes, launch at login, signing/notarization

### Takeaway
Both platforms expect automatic light/dark following, respect for reduced-motion/transparency settings, and native type (SF Pro via system font on macOS; Segoe UI Variable 14/20 body on Windows). Launch at login is `SMAppService.mainApp` on macOS and a startup registration on Windows; distribution outside stores requires Developer ID + hardened runtime + notarization + stapling on macOS, and code-signing is recommended on Windows for a persistent tray GUID. Typical popover/flyout widths in practice are ~320–360 px; Apple publishes no number.

### Cited Findings
- macOS: Liquid Glass adapts to "accessibility settings that reduce transparency or motion"; Apple says to test custom elements under these settings. — [Adopting Liquid Glass](https://developer.apple.com/documentation/technologyoverviews/adopting-liquid-glass)
- macOS reduce motion toggle: Accessibility > Display > Reduce motion; it drives `prefers-reduced-motion` in webviews. — [reduced-motion npm](https://www.npmjs.com/package/reduced-motion)
- Windows: Accessibility > Visual effects > Animation effects; "Animate controls and elements inside windows" unchecked sets `prefers-reduced-motion`. — [Vispero](https://vispero.com/?p=3749)
- Windows backdrops follow light/dark automatically unless tint properties are customised; WinUI 3 `SystemBackdropConfiguration.Theme` must be updated on `ActualThemeChanged`. — [Microsoft Learn, System backdrops](https://learn.microsoft.com/en-us/windows/apps/develop/ui/system-backdrops)
- Windows typography: Segoe UI Variable, Body 14/20, Caption 12/16, Semibold for emphasis. — [Fluent 2 typography](https://fluent2.microsoft.design/typography); [Microsoft Learn Typography](https://learn.microsoft.com/en-us/windows/apps/design/signature-experiences/typography)
- macOS menu bar height 24 pt; template images for menu bar extras. — [Apple HIG, The menu bar](https://developer.apple.com/design/human-interface-guidelines/the-menu-bar)
- Tray/menu icon sizes: Electron recommends 16×16 and 32×32@2x template images on macOS, `.ico` on Windows; Microsoft requires 16×16 and 32×32 icons via `LoadIconMetric`; Tauri guide uses 22×22 white-on-transparent. — [Electron Tray](https://www.electronjs.org/docs/latest/api/tray); [Microsoft Learn, Notification Area](https://learn.microsoft.com/en-us/windows/win32/shell/notification-area); [DEV Tauri guide](https://dev.to/hiyoyok/complete-guide-to-building-a-macos-menu-bar-app-with-tauri-v2-aji)
- Popover size example: the Tauri menu-bar guide uses a 360×540 non-resizable window with 18 pt corner radius. — [DEV Tauri guide](https://dev.to/hiyoyok/complete-guide-to-building-a-macos-menu-bar-app-with-tauri-v2-aji)
- Launch at login: `SMAppService.mainApp` (macOS 13+); read state from SMAppService, not local prefs. — [Apple docs](https://developer.apple.com/documentation/servicemanagement/smappservice/mainapp); [Nil Coalescing](https://nilcoalescing.com/blog/LaunchAtLoginSetting); Tauri `tauri-plugin-autostart` with `MacosLauncher::LaunchAgent` shows under Login Items. — [DEV Tauri guide](https://dev.to/hiyoyok/complete-guide-to-building-a-macos-menu-bar-app-with-tauri-v2-aji)
- Notarization (secondary summary of Apple docs): outside-App-Store distribution requires Developer ID signing, hardened runtime, `notarytool`, and stapling. — [evalops/agentd issue 33](https://github.com/evalops/agentd/issues/33); LaunchAtLogin-Legacy README: a debug flag "must be set to NO if you plan on distributing the build with codesigning". — [LaunchAtLogin-Legacy](https://github.com/sindresorhus/LaunchAtLogin-Legacy)
- Windows tray GUID persistence should be used "only with code-signed executables". — [Electron Tray](https://www.electronjs.org/docs/latest/api/tray)
- HIG keyboard: support standard shortcuts; iPad/macOS menu guidance. — [Apple HIG, The menu bar](https://developer.apple.com/design/human-interface-guidelines/the-menu-bar)
- Apple asks for an accessibility label on every icon-only control. — [Adopting Liquid Glass](https://developer.apple.com/documentation/technologyoverviews/adopting-liquid-glass)

### Inferences
- A popover of ~340 pt wide × content height (capped ≈ 500 pt, no scroll) fits the Control Center idiom on macOS and the Quick Settings idiom on Windows; make the height animate when sections expand (HIG: "animate the change").
- Treat reduced-motion as a first-class design state: replace spring/morph animations with crossfades, and reduced-transparency as the opaque default theme.

### Gaps
- Native reduced-motion APIs (`NSWorkspace.shared.accessibilityDisplayShouldReduceMotion`, WinRT `UISettings.AnimationsEnabled`) were not found in retrieved sources; only the OS setting locations and the web media query are sourced.
- Apple's notarization page body did not load (JS-rendered); requirements are cited only via secondary sources. Gatekeeper changes in macOS 26/27, if any, are unverified.
- Windows: no source retrieved for launch-at-login registration APIs (`StartupTask` for packaged apps / Run key for unpackaged) or for SmartScreen/EV-signing expectations in 2026.
- Keyboard-navigation specifics for popovers/flyouts (focus trapping, Esc to dismiss) were not found in either HIG or Fluent pages fetched.
