# Build on libmdr, not Plutoberth's archived client

Beyond Plutoberth's archived SonyHeadphonesClient, roughly sixty GitHub repositories now control Sony headphones from a desktop, almost all created in 2026, but only four carry real weight: **mos9527/SonyHeadphonesClient** (345 stars, C++, Windows/Linux/macOS/Web, the de-facto successor and home of the reusable `libmdr` protocol library), **marconvcm/sony-device-center** (283 stars, Qt 6, Windows/Linux/macOS, the press-covered "Sony Device Center"), **maniacx/BudsLink** (270 stars, multi-brand Linux Flatpak with Sony configs) and **AmitRajput-Dev/SonyBridge** (132 stars, native macOS menu-bar app, the only one with Homebrew install analytics) ([GitHub API](https://api.github.com/repos/mos9527/SonyHeadphonesClient); [GitHub API](https://api.github.com/repos/marconvcm/sony-device-center); [GitHub API](https://api.github.com/repos/maniacx/BudsLink); [GitHub API](https://api.github.com/repos/AmitRajput-Dev/SonyBridge)). Plutoberth's original remains the most-downloaded tool ever (**60,121** release downloads) but is archived, write-only, and cannot connect to anything newer than the WH-1000XM4, so every XM5/XM6/WF/LinkBuds owner must use a successor ([Releases API](https://api.github.com/repos/plutoberth/SonyHeadphonesClient/releases); [README](https://github.com/Plutoberth/SonyHeadphonesClient)). For newer models, mos9527 is the only client that documents hardware-verified full feature tables for the WH-1000XM6 and WF-1000XM6 plus WF-1000XM5, LinkBuds S/Open/Clip and WH-CH720N; Device Center and SonyBridge cover everyday controls but still carry XM6 readback bugs, ULT WEAR is verified only in SonyBridge and a dedicated CLI, and LinkBuds Fit appears in no project at all ([docs/device-support](https://github.com/mos9527/SonyHeadphonesClient/tree/v1-compat/docs/device-support); [sony-device-center README](https://github.com/marconvcm/sony-device-center#-supported-devices); [SonyBridge README](https://github.com/AmitRajput-Dev/SonyBridge#-supported-headphones)). For a developer building their own app, the strongest option is to **reuse mos9527's MIT-licensed `libmdr` + `libmdr-bt`** as the protocol engine and write your own UI on top, treating Gadgetbridge's AGPL-3.0 Java as a read-only specification; this is exactly what at least six 2026 projects (KDE widget, Rainmeter widget, Sony Tray, soundconnect-desktop, Sailfish Lauscher, aResiy/sony-control) already did ([README](https://github.com/mos9527/SonyHeadphonesClient#readme); [openrepos Lauscher](https://openrepos.net/node/12576); [sony-tray README](https://github.com/abhiinhii/sony-tray#credits)). Forking Plutoberth is the weakest path because its UUID and command set are compile-time constants on a 2019 protocol; building from scratch is defensible only if you need a Rust or Swift core without C++ FFI, and even then the protocol facts (one shared frame format, two opcode tables, per-model quirks, a one-connection-at-a-time limit, no official SDK) argue for porting from MIT sources rather than re-deriving the protocol.

The numbers tell a clear story about where users actually go. ## Plutoberth's 60,000 downloads sit on a 2019 protocol

Understanding why the original client is a dead end explains why its direct forks never took off. Plutoberth created the project in August 2020 after buying WH-1000XM3s and reverse-engineering the Android app "for intercompatibility purposes"; it shipped nine releases through v1.3.2 in April 2023, the author posted a "Looking for a new maintainer" issue in December 2022 that drew a single volunteer, and the repository was archived read-only on 2025-07-19 with a note pointing users to forks that "might work, but I haven't tested or reviewed them myself" ([README](https://github.com/Plutoberth/SonyHeadphonesClient/blob/master/README.md); [Issue #86](https://github.com/Plutoberth/SonyHeadphonesClient/issues/86); [GitHub API](https://api.github.com/repos/plutoberth/SonyHeadphonesClient)). Its feature set was always narrow: `Headphones.h` exposes exactly five setters (ambient sound control, focus on voice, ASM level, surround position, VPT type) backed by desired-value structs with no getters, `Constants.h` defines only two command types, and the README's own checklist leaves "Display battery life and fetch existing settings" and "Equalizer" unchecked; PRs adding EQ presets (#66, 2022) and XM4 Speak-to-Chat, ANC optimizer and multipoint (#103, 2023) were never merged ([Client/Headphones.h](https://github.com/Plutoberth/SonyHeadphonesClient/blob/master/Client/Headphones.h); [Client/Constants.h](https://github.com/Plutoberth/SonyHeadphonesClient/blob/master/Client/Constants.h); [PR #66](https://github.com/Plutoberth/SonyHeadphonesClient/pull/66); [PR #103](https://github.com/Plutoberth/SonyHeadphonesClient/pull/103)).

The structural problem is the protocol generation. The service UUID `96CC203E-5068-46ad-B32D-E316F5E069BA` is a compile-time constant and the opcode set is Sony's "MDR v1", so every device launched from mid-2021 onward, which uses the `jp.co.sony.songpal.mdr.link2` v2 service with UUID `956c7b26-d49a-4ba8-b03f-b17d393cb6e2`, fails with "Couldn't connect: 10049" on Windows or "could not connect to bluetooth socket" on Linux ([Client/IBluetoothConnector.h](https://github.com/Plutoberth/SonyHeadphonesClient/blob/master/Client/IBluetoothConnector.h); [Issue #29](https://github.com/Plutoberth/SonyHeadphonesClient/issues/29); [Issue #77](https://github.com/Plutoberth/SonyHeadphonesClient/issues/77)). The 82-comment "Headset Reports" megathread documents WF-1000XM4, WH-1000XM5, LinkBuds S, WH-CH720N, CH510/CH520, XB910N and CH710N all failing to connect, and the still-open "WH-1000-XM5 Support" issue (12 reactions, 19 comments) is where mos9527 first announced, on 2024-03-03, that ambient and NC settings worked on a WF-1000XM5 ([Issue #29](https://github.com/Plutoberth/SonyHeadphonesClient/issues/29); [Issue #77](https://github.com/Plutoberth/SonyHeadphonesClient/issues/77)). Because v2 support required restructuring rather than patching, the forks network is thin: no direct fork of Plutoberth has more than 7 stars, the top one (pasical's WH-XM5 fork) is itself archived, and mos9527's repository is technically not a fork at all (GitHub `fork=false`) but a recreated project that credits Plutoberth and inherits his commit history ([Forks API](https://api.github.com/repos/plutoberth/SonyHeadphonesClient/forks?sort=stargazers); [mos9527 GitHub API](https://api.github.com/repos/mos9527/SonyHeadphonesClient)).

## mos9527 alone documents full WH-1000XM6 and WF-1000XM6 coverage

On the newer models the user asked about, the gap between the leaders is wider than the star counts suggest. mos9527's `docs/device-support` folder carries per-model feature tables for WF-1000XM5, WF-1000XM6, WF-C510, WF-C700N, WF-L910, WF-LC900, WF-LS900N (LinkBuds S), WH-1000XM3, WH-1000XM5, WH-1000XM6 and WH-CH720N; the WH-1000XM6 table marks all sixteen features verified, including multipoint control, Speak to Chat, listening mode, 10-band equalizer, touch sensor, NC/AMB button assignment and voice assistant, with the firmware-specific caveat that only the Heavy/Clear/Hard/Soft/Custom EQ presets are accepted as of FW 3.0.0 ([docs/device-support](https://github.com/mos9527/SonyHeadphonesClient/tree/v1-compat/docs/device-support); [WH-1000XM6.md](https://github.com/mos9527/SonyHeadphonesClient/blob/v1-compat/docs/device-support/WH-1000XM6.md)). The WF-1000XM5 table is likewise fully green, and the WF-L910/WF-LC900 docs are the only coverage of the 2024-2025 LinkBuds Open/Clip models found anywhere, though the mapping of those model codes to marketing names was not independently verified and **LinkBuds Fit (WF-LS910N) appears in no project** ([WF-1000XM5.md](https://github.com/mos9527/SonyHeadphonesClient/blob/v1-compat/docs/device-support/WF-1000XM5.md); [docs/device-support](https://github.com/mos9527/SonyHeadphonesClient/tree/v1-compat/docs/device-support)).

Device Center and SonyBridge are strong everyday clients with honest but narrower verification. Device Center's README marks WH-1000XM5 and XM3 verified by the maintainer, XM4 and WF-1000XM6 verified by community reports, and the WH-1000XM6 only "partially working" because "noise-control readback remains unresolved, battery intermittent", with WF-1000XM5, ULT WEAR, LinkBuds S and CH720N untested and MDR-1000X known broken ([sony-device-center README](https://github.com/marconvcm/sony-device-center#-supported-devices)). SonyBridge is hardware-verified only on WH-CH720N and ULT WEAR (WH-ULT900N), lists XM5/XM6 as "expected", treats WF-1000XM5 as "controls work; battery format differs", and gives v1 devices NC/ambient only; SoundGuys' hands-on noted it "can resist switching modes when changes are made too frequently" and that users reported WH-1000XM4 crashes ([SonyBridge README](https://github.com/AmitRajput-Dev/SonyBridge#-supported-headphones); [SoundGuys](https://www.soundguys.com/sony-bluetooth-headphone-control-mac-os-160060/)). ULT WEAR is otherwise verified only in the dedicated macOS CLI sony-ult-ctl, while XMDeck, sbtfix and sony-tray list it as "should work" without hardware ([sony-ult-ctl](https://github.com/Leonard013/sony-ult-ctl); [sbtfix README](https://github.com/htsecurity/sbtfix#readme)). Feature breadth, notably, tracks library choice: the clients with near-complete feature lists are either built on mos9527's libmdr (kde-headphones, the Rainmeter widget, sony-tray) or run a full daemon architecture (Device Center, OpenSound, sony-headphones-linux), whereas hand-rolled Swift menu-bar apps typically stop at NC, ambient, battery and sometimes EQ ([kde-headphones README](https://github.com/RodiAda/kde-headphones#readme); [OpenSound](https://github.com/CpuJP/OpenSound); [xm6-macos-controller README](https://github.com/shellingtonshreyas/xm6-macos-controller#readme)).

Maintenance signals separate the sustainable from the one-weekend projects. Only four repositories show multi-person upkeep: mos9527 (23 contributors, commits on the day of research, a Windows co-maintainer credited for XM6 work), Device Center (12 contributors, six releases between 2026-09-10 and 2026-11-01, 35 open issues being triaged), BudsLink (30 contributors) and SonyBridge (7 contributors, releases July through October 2026) ([mos9527 Contributors API](https://api.github.com/repos/mos9527/SonyHeadphonesClient/contributors); [sony-device-center Releases](https://github.com/marconvcm/sony-device-center/releases); [BudsLink API](https://api.github.com/repos/maniacx/BudsLink); [SonyBridge Releases](https://github.com/AmitRajput-Dev/SonyBridge/releases)). Many of the rest (SonyCompanionApp, Ripthulhu/sony-xm-control, sevsev9/sonyctl, ibatra, sbtfix, VyomJain6904) are single-day or single-release bursts with no later commits, and the older tools (WinUI-SonyHeadphonesClient, sony-headphones-control-py, Obito1903) have been dead since 2023 ([SonyCompanionApp API](https://api.github.com/repos/whitebeard10/SonyCompanionApp); [WinUI API](https://api.github.com/repos/dustbin1415/WinUI-SonyHeadphonesClient); [Obito1903 API](https://api.github.com/repos/Obito1903/sony-headphones-ctl)). mos9527's one real weakness is release hygiene: its last tagged release (1.4.4, 2025-09-27) is explicitly labelled a "legacy branch" build, current work on the default `v1-compat` branch ships only as nightlies and the Web PWA, and there are separate `master`, `rewrite` and `web-ble` branches, so users wanting stable binaries are currently pointed at nightly.link ([Releases](https://github.com/mos9527/SonyHeadphonesClient/releases); [README](https://github.com/mos9527/SonyHeadphonesClient#readme)). The issue trackers across all projects converge on the same complaints: unsupported-model connection failures, Bluetooth socket errors (Windows 10049, Linux RFCOMM channel lookups), unsigned binaries tripping Gatekeeper and SmartScreen (no free project pays for signing), and state/readback bugs such as battery missing or EQ reverting, while the most-reacted feature request on mos9527 is a CLI for automation and keybinds ([mos9527 Issue #15](https://github.com/mos9527/SonyHeadphonesClient/issues/15); [sony-device-center Issue #57](https://github.com/marconvcm/sony-device-center/issues/57); [sony-device-center Issue #11](https://github.com/marconvcm/sony-device-center/issues/11); [SonyBridge Issue #27](https://github.com/AmitRajput-Dev/SonyBridge/issues/27)).

## One framer, two opcode tables and a one-connection limit shape every design

A developer's build-versus-reuse decision should rest on five protocol and platform facts. First, there is **no official SDK and no official desktop app**: Sony's support article 00269130 says "There is no PC app available", the only public Sony Audio Control API covers networked soundbars and receivers over HTTP/JSON, and every project calls the headphone protocol unpublished ([Sony Canada](https://www.sony.ca/en/electronics/support/software/00269130); [Home Assistant Songpal](https://www.home-assistant.io/integrations/songpal/); [overheard](https://github.com/andreabedini/overheard)). Second, the wire format is simple and shared across generations: `0x3E | type | seq | len(u32 BE) | payload | checksum | 0x3C`, with `0x3C/0x3D/0x3E` escaped via `0x3D, (b & 0xEF)`, an 8-bit sum checksum, and stop-and-wait ARQ where each frame is acknowledged with the flipped sequence number; the escape mask is a known trap because it only bites on payloads containing those bytes, such as the 16000 Hz EQ band value `0x3E80` ([Message.java](https://codeberg.org/Freeyourgadget/Gadgetbridge/raw/branch/master/app/src/main/java/nodomain/freeyourgadget/gadgetbridge/service/devices/sony/headphones/protocol/Message.java); [hush](https://github.com/ismoilovdevml/hush)). Third, "v1 versus v2" is a different SDP service UUID plus a largely different opcode table, not a different protocol: Gadgetbridge detects the version from the init reply length (4 bytes v1, 8 bytes v2), models v2 as `SonyProtocolImplV2 extends SonyProtocolImplV1` with about thirty overridden request builders, and the collision where `0x22` means POWER_OFF in v1 but BATTERY request in v2 has already caused a real SonyBridge bug ([SonyHeadphonesProtocol.java](https://codeberg.org/Freeyourgadget/Gadgetbridge/raw/branch/master/app/src/main/java/nodomain/freeyourgadget/gadgetbridge/service/devices/sony/headphones/SonyHeadphonesProtocol.java); [PayloadTypeV2.java](https://codeberg.org/Freeyourgadget/Gadgetbridge/raw/branch/master/app/src/main/java/nodomain/freeyourgadget/gadgetbridge/service/devices/sony/headphones/protocol/impl/v2/PayloadTypeV2.java); [SonyBridge releases](https://github.com/AmitRajput-Dev/SonyBridge/releases)). The model split is clean: v1 covers WH-1000XM2/XM3/XM4, WF-1000XM3, WF-SP800N, XB900N, MDR-XB950BT and earlier; v2 covers WF-1000XM4/XM5/XM6, WH-1000XM5/XM6, LinkBuds and LinkBuds S, WH-CH720N/CH520, XB910N, ULT WEAR and the WF-C series ([Gadgetbridge init comments](https://codeberg.org/Freeyourgadget/Gadgetbridge/raw/branch/master/app/src/main/java/nodomain/freeyourgadget/gadgetbridge/service/devices/sony/headphones/SonyHeadphonesProtocol.java); [sony-device-center model table](https://github.com/marconvcm/sony-device-center)).

Fourth, the real long-tail work is per-model quirks inside v2, which argues for runtime capability discovery over static tables. On connect, v2 devices answer a `06 00` request on both command tables with a `07 00` list of supported functions; the WH-1000XM6 answers a different ambient-sound inquiry sub-type (`0x19` round-trips while `0x15`/`0x22` get no reply on fw 3.1.5), moved wearing detection to the SYSTEM family, put multipoint management on the second message table, and uses a 10-band EQ with raw levels 0-12 and no Clear Bass, so hush and mos9527 both probe sub-types and EQ layouts at connect time and ship built-in frame loggers to crowd-source new model reports ([Resonance PROTOCOL.md](https://github.com/FireWall-code/Resonance-for-Sound-Connect/blob/main/docs/PROTOCOL.md); [hush](https://github.com/ismoilovdevml/hush); [xm6-control](https://github.com/ruimartins23/xm6-control); [mos9527 DEVELOPER.md](https://github.com/mos9527/SonyHeadphonesClient/blob/v1-compat/DEVELOPER.md)). Sony's 2026 firmware updates expanding LE Audio on the XM6 and WF-1000XM5 add a further risk: switching to LE Audio drops the Classic RFCOMM control link, and only one project claims a verified BLE control path ([Notebookcheck](https://www.notebookcheck.net/Sony-releases-major-updates-to-WH-1000XM6-and-WF-1000XM5-with-long-awaited-improvements.1048476.0.html); [Resonance PROTOCOL.md](https://github.com/FireWall-code/Resonance-for-Sound-Connect/blob/main/docs/PROTOCOL.md); [EncoDeck](https://github.com/TIANLI0/EncoDeck)). Fifth, **Sony headsets accept only one control connection at a time**, so when the phone app connects the desktop client drops, and several projects (hush, XMDeck, VyomJain6904's daemon) broker or release the channel on demand; the RFCOMM channel number also varies per model (9, 15 or 18 in reports) and must come from SDP or an OS-level UUID connect ([connect-tray](https://github.com/pdimu/connect-tray); [ConnectFlyout README](https://github.com/artistro08/ConnectFlyout); [mdr-protocol](https://github.com/AndreasOlofsson/mdr-protocol); [sony-ult-ctl](https://github.com/Leonard013/sony-ult-ctl)).

Platform transports are small but must be native. Windows works best through Winsock (`AF_BTH`/`BTHPROTO_RFCOMM` with `serviceClassId` set so the system resolves the channel without an SDP query and without a manifest capability), WinRT's `RfcommDeviceService` being needed only for packaged Store apps; macOS uses IOBluetooth's `openRFCOMMChannelSync` with the caveat that IOBluetooth is not thread-safe and delegates must run on the main run loop, which pushes toward a Swift/ObjC transport layer even under a C++ or Rust core; Linux uses BlueZ RFCOMM sockets or the D-Bus Profile API, with the `bluer` crate as the Rust route ([Bluetooth and connect (Win32)](https://learn.microsoft.com/en-us/windows/win32/bluetooth/bluetooth-and-connect); [RfcommDeviceService docs](https://learn.microsoft.com/en-us/uwp/api/windows.devices.bluetooth.rfcomm.rfcommdeviceservice); [sony-xm6-web](https://github.com/andersnsouza/sony-xm6-web); [bluer docs](https://docs.rs/bluer)). None of the generic cross-platform wrappers (32feet.NET, Dart `bluetooth_rfcomm`, Node `bluetooth-serial-port`) is proven on Sony devices and both 32feet and `bluetooth_rfcomm` lack reliable SDP on Linux, which is why every surveyed client wrote its own three backends; Web Serial is the one surprising alternative, used by mos9527's PWA, Nullpoint and usering-around's WASM GUI to drive the SPP virtual COM port from Chrome 89+ or Firefox 151+ ([32feet wiki](https://github.com/inthehand/32feet/wiki); [bluetooth_rfcomm](https://pub.dev/packages/bluetooth_rfcomm); [mos9527 README](https://github.com/mos9527/SonyHeadphonesClient); [nullpoint](https://github.com/mehrshaad/nullpoint)). LDAC is a platform limit no control app can fix: Windows lacks native LDAC and macOS restricts Bluetooth to AAC ([SoundGuys Win/Linux](https://www.soundguys.com/sony-headphones-windows-linux-unofficial-app-162956/); [SoundGuys Mac](https://www.soundguys.com/sony-bluetooth-headphone-control-mac-os-160060/)).

## Reuse MIT libmdr, read AGPL Gadgetbridge, skip the Plutoberth fork

Licensing draws the sharpest line between the options. Gadgetbridge is the most battle-tested and broadly verified implementation (19 Sony coordinators on master, a dedicated maintainer since 2021, new models repeatedly added from user HCI logs without device access), and nearly every 2025-2026 client cites it as the byte-layout reference, but it is **AGPL-3.0** and its transport is Android `BluetoothSocket`; the community pattern for permissive projects is therefore explicit, with Fanxingkeming, hush and marnunez/sonyctl stating that AGPL code "was read but not copied", while gabamnml and DaanHessen chose AGPL "matching Gadgetbridge" because their opcode tables follow its code ([Gadgetbridge LICENSE](https://codeberg.org/Freeyourgadget/Gadgetbridge/raw/branch/master/LICENSE); [coordinators dir](https://codeberg.org/Freeyourgadget/Gadgetbridge/src/branch/master/app/src/main/java/nodomain/freeyourgadget/gadgetbridge/devices/sony/headphones/coordinators); [Fanxingkeming](https://github.com/Fanxingkeming/sony-headphones-control); [hush](https://github.com/ismoilovdevml/hush); [gabamnml](https://github.com/gabamnml/omarchy-sony-headphones)). Gadgetbridge also has gaps that matter for this question: it has no coordinator for WF-1000XM6, LinkBuds Fit/Open/Clip, WH-CH520 or WH-XB910N, and its WH-1000XM6 coordinator is flagged experimental with the comment "Battery, equalizer, and quite a few others probably not working" ([SonyWH1000XM6Coordinator.java](https://codeberg.org/Freeyourgadget/Gadgetbridge/raw/branch/master/app/src/main/java/nodomain/freeyourgadget/gadgetbridge/devices/sony/headphones/coordinators/SonyWH1000XM6Coordinator.java); [gadgetbridge.org Sony page](https://gadgetbridge.org/gadgets/headphones/sony/)). Nothing is published on PyPI, crates.io, npm, pub.dev or NuGet as a Sony protocol library; every reusable piece is an in-repo module of an app ([pub.dev search](https://pub.dev/packages/headphones_detection); [python-songpal on PyPI](https://pypi.org/project/python-songpal)).

That makes mos9527's `libmdr` the strongest reuse target by a wide margin. It is MIT, C++20, split into a platform-agnostic `libmdr` (framing, V1+V2 opcode tables, generated command definitions) and a `libmdr-bt` layer with Windows, Linux, macOS, iOS, Emscripten and Null backends, exposes CMake options for a stub backend "for platform porting" and optional BLE, has Python bindings in a sibling repo, and already covers the 2024-2026 models Gadgetbridge lacks ([libmdr README](https://github.com/mos9527/SonyHeadphonesClient/blob/v1-compat/libmdr/README.md); [DEVELOPER.md](https://github.com/mos9527/SonyHeadphonesClient/blob/v1-compat/DEVELOPER.md); [libmdr-py](https://github.com/mos9527/libmdr-py)). Its demonstrated reuse record is the decisive evidence: RodiAda/kde-headphones (C++), GlobularShield/XMBar (Swift/AppKit), the icdmkg2 Rainmeter widget, AlexandForests/sonytuibar, B-Howell/soundconnect-desktop (Tauri), VyomJain6904/sony-headphones-linux and the Sailfish app Lauscher all consume libmdr directly, and abhiinhii/sony-tray (C#/Swift) and aResiy/sony-control (Rust) ported its protocol code into other languages, so both the "link it" and "transliterate it" paths are proven ([kde-headphones README](https://github.com/RodiAda/kde-headphones#supported-headphones); [XMBar README](https://github.com/GlobularShield/XMBar); [soundconnect-desktop](https://github.com/B-Howell/soundconnect-desktop); [openrepos Lauscher](https://openrepos.net/node/12576); [sony-tray README](https://github.com/abhiinhii/sony-tray#credits); [aResiy/sony-control](https://github.com/aResiy/sony-control)). Its risks are a single core maintainer ("We *really* need more volunteers"), pre-1.0 branch churn, and C++ FFI if your UI language is Rust, .NET or Swift ([README (v1-compat)](https://github.com/mos9527/SonyHeadphonesClient/blob/v1-compat/README.md)).

The runner-up for reuse is Device Center's `sony-protocol`/`sony-transport`/`sony-core` stack, which is also MIT, has "111 hardware-free protocol tests", ships a daemon and CLI, and already powers a second app (ConnectFlyout on the Microsoft Store); two cautions are its "heavy AI assistance" disclaimer and the fact that its README prints V1/V2 service UUIDs (`96CC203E-50F8-...`, `956C7B26-B496-...`) that disagree with Gadgetbridge and four independent projects, which is almost certainly a documentation error but means its byte layouts should be checked against Gadgetbridge before you depend on them ([sony-device-center README](https://github.com/marconvcm/sony-device-center); [ConnectFlyout README](https://github.com/artistro08/ConnectFlyout#readme); [SonyHeadphonesSupport.java](https://codeberg.org/Freeyourgadget/Gadgetbridge/raw/branch/master/app/src/main/java/nodomain/freeyourgadget/gadgetbridge/service/devices/sony/headphones/SonyHeadphonesSupport.java)). For a Rust-first build, andreabedini/overheard offers sans-IO `mdr-frame`/`mdr-proto`/`mdr-session` crates under MIT/Apache-2.0 verified on WF-C700N and WH-1000XM6, but it is seven commits old, Linux-only and self-described as "early and experimental" ([overheard](https://github.com/andreabedini/overheard)). Forking Plutoberth ranks last: the archived code is v1-only, write-only, has its UUID and command set as compile-time constants, and the only forks that reached v2 did so by rewriting, which is precisely what mos9527 already finished ([Client/Constants.h](https://github.com/Plutoberth/SonyHeadphonesClient/blob/master/Client/Constants.h); [mos9527 README (master)](https://github.com/mos9527/SonyHeadphonesClient/blob/master/README.md)).

Building from scratch is only rational if you are committed to a non-C++ core and want no FFI, and even then the evidence says to port from MIT sources (mos9527 and Plutoberth) and CC0 documentation (ohm-app) rather than re-derive the protocol from APK captures; Resonance's `PROTOCOL.md`, reconstructed from Sound Connect 13.3.0 and verified on a WF-1000XM6, is the best prose reference for v2 capability discovery but its code is now PolyForm Noncommercial, so treat it as documentation only ([ohm-app](https://github.com/ohm-app/sony-headphones-bluetooth-documentation); [Resonance](https://github.com/FireWall-code/Resonance-for-Sound-Connect); [Resonance PROTOCOL.md](https://github.com/FireWall-code/Resonance-for-Sound-Connect/blob/main/docs/PROTOCOL.md)). On the legal side, no project reports any action from Sony in more than five years, every project carries a "not affiliated with or endorsed by Sony" disclaimer and frames the work as interoperability, and generic Sony EULAs prohibit reverse engineering only "except where applicable laws make that conduct impossible to prohibit"; the Sound Connect app's own terms were not located, and nothing in the research addresses Sony's trademark policy, so a new app should avoid "Sony" or "Sound Connect" in its name as several projects deliberately do ([Plutoberth README](https://github.com/Plutoberth/SonyHeadphonesClient); [connect-tray](https://github.com/pdimu/connect-tray); [Sony EULA (en-aus)](https://helpguide.sony.net/di/el23/v1/en-aus/index.html); [GitHub topic listing](https://github.com/topics/sony-headphones)).

## Conclusion

The market has already decided what the protocol layer should be: within eighteen months of mos9527 announcing XM5 support in Plutoberth's issue tracker, `libmdr` became the shared engine under a KDE widget, a Rainmeter skin, a Windows tray app, a Tauri UI, a Sailfish app and a Rust port, while Device Center's stack became the second engine under a Microsoft Store app. A new client that re-derives Sony's framing and opcode tables adds a sixty-first implementation to a field where the protocol is a solved problem and the unsolved problems are elsewhere. The developer's differentiation budget should instead go to what no project has: signed and notarized binaries, Flathub/winget/Homebrew-core distribution (BudsLink's 4,567 monthly Flathub installs show the demand a store listing unlocks), a CLI and global hotkeys for automation, a capability-discovery layer plus frame logger so community XM6/WF-XM6/LinkBuds reports become support without maintainer hardware, and a connection broker that hands the single control channel back to the phone app gracefully.

The strongest plan is therefore a thin native UI per platform on top of mos9527's `libmdr` and `libmdr-bt`, with Gadgetbridge open in a second window as the reference you read but never paste, and with contributions pushed upstream to libmdr so that the single-maintainer risk shrinks rather than fragmenting further. Two things could change this calculus and are worth watching: mos9527 merging `v1-compat` into a tagged release (which would make it the first client to cover XM3 through WF-1000XM6 in one binary and remove its main adoption friction) and Sony's LE Audio firmware roll-out, which if it drops the Classic RFCOMM control path on new devices would reward whichever engine first ships a verified GATT transport.
