# Building a new Sony MDR protocol library beyond Sound Connect — discovery, command tables, hidden capabilities, firmware path, foundation choice (as of 2026-11-07)

Scope: what a developer needs to write their own Sony headphone ("MDR" / "TandemFamily") protocol library and add features Sony's Sound Connect app never offered. Repo metadata (license, stars, last push) read from the GitHub/Codeberg APIs on 2026-11-07; source files read from default branches the same day. Evidence is labelled; unsupported items are in Gaps.

Related notes in this folder (not repeated): `protocol_and_libraries.md` (frame format, v1/v2 differences, platform RFCOMM access, official SDK status) and `alternative_clients.md` (client inventory).

## Key question 1: How has the community discovered commands so far (methods and tooling)?

### Takeaway
Five methods are in use; the highest-yield one in 2026 is static extraction from Sony's own app binaries. mos9527's `tooling/ida` pipeline pulls the complete v1/v2 payload and enum definitions out of the Sound Connect iOS binary (J2ObjC-compiled Java, so Java class/field names survive) and renders them to C++ headers; Resonance and fix-whxm4-voice decompile the Android APK with `jadx`. Dynamic capture (Android HCI snoop → Wireshark, plus frame recorders built into mos9527/Resonance/hush) confirms layouts and reveals which variant a given model answers. No single Sony-specific tutorial exists; the pieces are spread across the repos below.

### Cited Findings — static extraction from the iOS app (mos9527 IDA pipeline)
- Pipeline in `tooling/ida/README.md`: obtain the Sound Connect iOS app, extract the decrypted ARM64 Mach-O containing the J2ObjC classes, load in IDA with Hex-Rays, preserve the Objective-C/J2ObjC symbol names, then run `tooling/ida/j2objc/extract_all.py` via File > Script file. It writes `inventory.json`, `v*_t*.json` (normalized enum/payload IR) and `v*_t*.manifest.json` (every candidate + classification). The README is labelled "LLM generated guide/scripts. Follow at your own discretion." — [tooling/ida/README.md](https://github.com/mos9527/SonyHeadphonesClient/blob/v1-compat/tooling/ida/README.md)
- Extraction is "evidence based and fail closed": it resolves J2ObjC descriptors through class metadata, correlates static index/size constants with getter/serializer byte access, and follows parser-helper allocations for polymorphic variants. Rendering headers does NOT need IDA: `python -m tooling.ida.j2objc.render` writes `libmdr/include/mdr/Generated/ProtocolV{1,2}{,T1,T2}.hpp` from the checked-in IR. — [tooling/ida/README.md](https://github.com/mos9527/SonyHeadphonesClient/blob/v1-compat/tooling/ida/README.md)
- `extract_all.py` counts serializers by scanning classes prefixed `THMSGV{version}T{table}` for `getCommandStream` (v1 t1) or `parseBytesWith…` selectors; expected inventory hard-coded as v1t1 101 enums/160 serializers, v1t2 12/47, v2t1 111/585, v2t2 47/300. — [extract_all.py](https://github.com/mos9527/SonyHeadphonesClient/blob/v1-compat/tooling/ida/j2objc/extract_all.py)
- `inventory.json` records the analysed binary SHA-256 and totals: v2_t1 1412 candidates → 623 payload declarations/111 enums/585 serializers; v2_t2 693 → 306/47/300; v1_t1 317 payload declarations; v1_t2 48. The generated headers carry the original Java class names as comments (e.g. `// THMSGV2T1UpdtSetParamTandemStartTransfer`), so cross-referencing an APK decompile is trivial. — [inventory.json](https://github.com/mos9527/SonyHeadphonesClient/blob/v1-compat/tooling/ida/generated/inventory.json)
- On iOS, MDR rides External Accessory (iAP2) protocols `jp.co.sony.songpal.mdr.link` (V1) and `jp.co.sony.songpal.mdr.link2` (V2); only one app can hold the accessory session, so Sound Connect must be quit. — [DEVELOPER.md](https://github.com/mos9527/SonyHeadphonesClient/blob/v1-compat/DEVELOPER.md)

### Cited Findings — static extraction from the Android APK (jadx)
- Resonance `docs/PROTOCOL.md` was "Reconstructed for interoperability from Sound Connect 13.3.0 (`com.sony.songpal.mdr`, version code 130305109) and verified on a WF-1000XM6, firmware 2.0.5"; rows carry evidence levels [App]/[Device]/[Tested]. — [Resonance PROTOCOL.md](https://github.com/FireWall-code/Resonance-for-Sound-Connect/blob/main/docs/PROTOCOL.md)
- fix-whxm4-voice `docs/upload-protocol.md`: Sound Connect 12.4.2 (version code 120425009) "was decompiled with `jadx --no-res` and never run"; the base APK is signed by `CN=mobile.link, O=Sony Corporation`; the bundled Airoha SDK reports `Ver:1.5.7.2025052218`. Class names such as `AirohaFotaAdapterSony`, `FotaControl2811`, `MtkUpdateController` survive; others (`p466p2.c`) are obfuscated and only hold for that build. — [upload-protocol.md](https://github.com/aaron-p1/fix-whxm4-voice/blob/main/docs/upload-protocol.md)
- AndreasOlofsson/mdr-protocol `reverse_engineering.md`: used dex2jar + fernflower (+ apktool for what fernflower missed). "The code is obfuscated but enums keep their original names so no guessing as to what values mean is necessary. The interesting parts are in the package `com.sony.songpal.tandemfamily.message.mdr`." — [reverse_engineering.md](https://github.com/AndreasOlofsson/mdr-protocol/blob/master/reverse_engineering.md)
- The GitHub-stamp / certificate detail means decompiling from the signed Play APK gives the richest symbol set (enum names intact).

### Cited Findings — dynamic capture (HCI snoop / Wireshark / in-app recorders)
- Gadgetbridge's BT reverse-engineering wiki: enable Developer options + "Enable Bluetooth HCI snoop log", toggle BT off/on, drive the vendor app, pull `data/misc/bluetooth/logs/btsnoop_hci.log` (via `adb bugreport`, `adb pull`, or `adb root`), open in Wireshark, filter by device MAC (`bluetooth.dst == …`), use marker commands around the unknown action, and "Export specific packets → Export as Symbian OS btsnoop" (MACs reset to 00:00 in exports). It also advises checking existing Gadgetbridge sources first and prefers Frida over APK decompilation. — [Gadgetbridge wiki: BT-Protocol-Reverse-Engineering](https://codeberg.org/Freeyourgadget/Gadgetbridge/wiki/BT-Protocol-Reverse-Engineering)
- Original Plutoberth discovery method (guilhermealbm, 2021): started with Android Bluetooth HCI Snoop + Wireshark ("extremely confusing"), then found that toggling the ANC button triggers Android's own `handleBluetoothA2dpActiveDeviceChangeExt` logging; but "alternating between equalizer profiles doesn't generate any record" — "To certain features, reverse-engineer the data format is the only alternative." — [Plutoberth PR #36 comment](https://github.com/Plutoberth/SonyHeadphonesClient/pull/36#issuecomment-795633877)
- mos9527 ships a Protocol Debugger (CMake `MDR_CLIENT_DEBUGGER`, default on in nightly CI): "view, replay, modify and send manipulated packets to a real device." The client records with `--record <folder>` and replays with `--replay <file/folder>` or drag-and-drop; `tooling/scrub-capture.py` strips paired-device names/addresses and track metadata with equal-length placeholders so captures become test fixtures. On an unexpected disconnect it prompts to dump the last packet/session. — [DEVELOPER.md](https://github.com/mos9527/SonyHeadphonesClient/blob/v1-compat/DEVELOPER.md), [tests/README.md](https://github.com/mos9527/SonyHeadphonesClient/blob/v1-compat/tests/README.md)
- Resonance has a CLI deepscan/test workflow: `resonance-cli deepscan > scan.txt` (reads only), `resonance-cli test` changes each supported setting, waits for confirmation, then restores and prints PASS/FAIL; `resonance-cli replay <folder>` decodes a `.bin` capture to JSON. — [Resonance CONTRIBUTING.md](https://github.com/FireWall-code/Resonance-for-Sound-Connect/blob/main/CONTRIBUTING.md)
- hush exposes `hush raw "66 19"` to send one frame and print the reply (but subject to an allow-list, see Q5). — [hush README](https://github.com/ismoilovdevml/hush)
- A requested but not-yet-built tool: BudsLink's "Interactive Bluetooth Device Profiler / Snooping Wizard" proposal — connect buds to both phone and Linux (multipoint), arm a listener, toggle a setting in the phone app, and the tool isolates the delta packet and tags it, auto-compiling a `deviceConfig.js`. This is a design proposal, not shipped. — [BudsLink issue #84](https://github.com/maniacx/BudsLink/issues/84)

### Cited Findings — the capability-discovery handshake (06/07)
- At connection, `CONNECT_GET_SUPPORT_FUNCTION` (command `0x06`, sent on both table 1 and table 2) returns `0x07 00 <n> (<function> <priority>)×n` — the list of functions the model supports; "this is how an app adapts its UI to each model." Each function type names the variant a model implements, and the variant decides the inquired type and payload layout. Resonance only queries declared functions; undeclared models fall back to the WF-1000XM6 set. — [Resonance PROTOCOL.md §3, §4b](https://github.com/FireWall-code/Resonance-for-Sound-Connect/blob/main/docs/PROTOCOL.md)
- In libmdr the opcodes are `CONNECT_GET_SUPPORT_FUNCTION = 0x06` / `CONNECT_RET_SUPPORT_FUNCTION = 0x07`, plus the group pattern `GET_CAPABILITY`/`RET_CAPABILITY` per feature group (e.g. `0xD0`/`0xD1` general settings, `0xF0`/`0xF1` system). The reply is a length-prefixed array (`ConnectRetSupportFunction` → `MDRPodArray<SupportFunction>`). — [ProtocolV2T1Enum.hpp](https://github.com/mos9527/SonyHeadphonesClient/blob/v1-compat/libmdr/include/mdr/Generated/ProtocolV2T1Enum.hpp), [DEVELOPER.md](https://github.com/mos9527/SonyHeadphonesClient/blob/v1-compat/DEVELOPER.md)
- Device Center implements this as a dedicated `CapabilityDiscovery` class with sync/async "probe unknown device feature by feature" plus a `CapabilityCache` keyed by model/address. — [CapabilityDiscovery.h](https://github.com/marconvcm/sony-device-center/blob/main/libs/sony-protocol/include/sony/protocol/CapabilityDiscovery.h)
- General settings are self-describing: `GET_CAPABILITY` returns slot + type (00 switch / 01 list) + format + name + summary strings, with identifiers like `SIDETONE_SETTING`, `MULTIPOINT_SETTING`, `TWS_ONE_SIDE_USE_NCASM_SETTING`, `TAP_SENSITIVITY_SETTING` and list choices `<name>_ELEM_LOW/_HIGH`. So a new client can enumerate many settings generically without hard-coding them. — [Resonance PROTOCOL.md §4b](https://github.com/FireWall-code/Resonance-for-Sound-Connect/blob/main/docs/PROTOCOL.md)

### Inferences
- The iOS J2ObjC route (mos9527) is strictly superior for building a *complete* table: it yields machine-checkable IR for all four tables in one pass, versus APK decompile which still gives obfuscated helper names. A new library should seed its command table from mos9527's checked-in `tooling/ida/generated/*.json` (MIT) and use HCI capture only to verify per-model variants.
- The `06/07` handshake plus self-describing general settings means a well-built new library can be largely model-agnostic (capability-gated), which is exactly what overheard, hush, Resonance and Device Center all converged on independently.

### Gaps
- No public Sony-specific end-to-end tutorial combines "capture → identify opcode → write codec"; the Gadgetbridge wiki is generic and its Sony examples are ATT/BLE-flavoured, whereas Sony control is RFCOMM/SPP.

## Key question 2: Which project has the most complete v2 opcode/sub-type table (including table 2 / 0x0E)?

### Takeaway
mos9527's libmdr is by far the most complete and the only one that is machine-generated for all four tables (v1/v2 × table1/table2); its v2 table-1 enum lists ~150 command opcodes and dozens of inquired-type enums, and v2 table-2 is fully generated too (306 payload declarations). Gadgetbridge's `PayloadTypeV2.java` is the most-tested hand-written table but is small (≈24 opcodes) and, notably, defines NO `COMMAND_2`/table-2 (0x0E) entries at all. Resonance's PROTOCOL.md is the best human-readable table and explicitly documents both table 1 and table 2 group maps.

### Cited Findings — mos9527 libmdr (most complete)
- v2 table-1 `Command` enum (opcode : value) is the canonical group grid. Groups by high nibble: `00` connect (00–07 incl. `CONNECT_GET/RET_SUPPORT_FUNCTION` 06/07), `0x0F GET_TEST`, `10` common, `20` power, `30` UPDT (firmware update, incl. `UPDT_TRANSFER_DATA=0x3E`), `40` LEA (LE Audio, incl. extended param 4A–4D), `50` EQEBB (equalizer, incl. `EQEBB_GET/RET_EXTENDED_INFO` 5A/5B), `60` NCASM, `70` SENSE, `80` OPT (optimizer), `90` ALERT, `A0` PLAY, `B0` SAR_AUTO_PLAY, `C0` LOG (`LOG_SET_STATUS=0xC4`, `LOG_NTFY_PARAM=0xC9`), `D0` GENERAL_SETTING, `E0` AUDIO, `F0` SYSTEM (incl. ext param FA–FD). — [ProtocolV2T1Enum.hpp](https://github.com/mos9527/SonyHeadphonesClient/blob/v1-compat/libmdr/include/mdr/Generated/ProtocolV2T1Enum.hpp)
- Rich inquired-type enums give the sub-type space, e.g. `SystemInquiredType` (VIBRATOR 00 … ASSIGNABLE_SETTINGS 03, VOICE_ASSISTANT_SETTINGS 04, CALL_SETTINGS 08, RESET_SETTINGS 09, FACE_TAP_TEST_MODE 0B, QUICK_ACCESS 0D, HEAD_GESTURE_ON_OFF 0F, HEAD_GESTURE_TRAINING 10), `PowerInquiredType` (BATTERY 00 … BATTERY_SAFE_MODE 0B, CARING_CHARGE 0C, BT_STANDBY 0D, STAMINA 0E), `AudioInquiredType` (CONNECTION_MODE 00, UPSCALING 01, BGM_MODE 03, UPMIX_CINEMA 04, VOICE_CONTENTS 06, SOUND_LEAKAGE_REDUCTION 07), `LogInquiredType` (ACTION_LOG_NOTIFIER 00, TIME_SERIES_OPERATIONLOG_NOTIFIER 01, SOUND_DROPOUT_NOTIFIER 02). — [ProtocolV2T1.hpp](https://github.com/mos9527/SonyHeadphonesClient/blob/v1-compat/libmdr/include/mdr/Generated/ProtocolV2T1.hpp)
- Test-mode / factory enums present: `NcTestModeOperation` (TEST_MODE_START/FINISH), `FaceTapTestModeOperation` (START/FINISH, OUT_OF_RANGE 0x99), `CallSettingsTestSoundControl` (START), `EarpieceFittingDetectionOperation`, `ResetType` (SETTINGS_ONLY 00 / FACTORY_RESET 01). — [ProtocolV2T1.hpp](https://github.com/mos9527/SonyHeadphonesClient/blob/v1-compat/libmdr/include/mdr/Generated/ProtocolV2T1.hpp)
- Table 2 (v2 t2) is also fully generated (306 payload declarations, 47 enums, 300 serializers per inventory.json); it covers power/battery-care, peripherals (paired-device management), voice guidance, safe listening, party, system. — [inventory.json](https://github.com/mos9527/SonyHeadphonesClient/blob/v1-compat/tooling/ida/generated/inventory.json)

### Cited Findings — what clients list but do NOT implement
- libmdr defines the full enum/struct table for all four tables, but the `client`'s own state machine (`HeadphonesV2T1.cpp`) only reacts to a subset of notify/ret opcodes; i.e. the serialization layer is complete, the high-level feature wiring is not. Many generated structs (SAR auto-play, head gesture, optimizer, LEA extended) exist with no UI. — [HeadphonesV2T1.cpp](https://github.com/mos9527/SonyHeadphonesClient/blob/v1-compat/libmdr/src/HeadphonesV2T1.cpp)
- Gadgetbridge `PayloadTypeV2.java` lists ~24 opcodes, ALL `MessageType.COMMAND_1` (0x0C); it defines NO `COMMAND_2` (0x0E) entries despite `MessageType` enumerating `COMMAND_2(0x0e)`. So Gadgetbridge's v2 support is table-1 only. — [PayloadTypeV2.java](https://codeberg.org/Freeyourgadget/Gadgetbridge/src/branch/master/app/src/main/java/nodomain/freeyourgadget/gadgetbridge/service/devices/sony/headphones/protocol/impl/v2/PayloadTypeV2.java), [MessageType.java](https://codeberg.org/Freeyourgadget/Gadgetbridge/src/branch/master/app/src/main/java/nodomain/freeyourgadget/gadgetbridge/service/devices/sony/headphones/protocol/MessageType.java)
- Gadgetbridge `SonyProtocolImplV2.java` has many `LOG.warn("… not implemented for V2")` stubs: noise-cancelling optimizer, sound position, surround mode, volume, touch sensor, JSON, virtual sound — i.e. opcodes acknowledged as unimplemented on v2. — [SonyProtocolImplV2.java](https://codeberg.org/Freeyourgadget/Gadgetbridge/src/branch/master/app/src/main/java/nodomain/freeyourgadget/gadgetbridge/service/devices/sony/headphones/protocol/impl/v2/SonyProtocolImplV2.java)
- Resonance PROTOCOL.md documents table-2 groups explicitly (`20` power, `30` peripherals, `40` voice guidance, `50` safe listening, `60` LE Audio, `70` party, `F0` system) and gives concrete T2 opcodes: battery care T2 `26/28 01`, voice guidance T2 `46/48 01`, voice-guidance volume T2 `46/48 20`, remembered devices T2 `36 02`, connect/disconnect/forget T2 `3C 02`, switch audio source T2 `3C 01`, pairing mode T2 `34 02`, safe-listening level `5A/5B` T2. — [Resonance PROTOCOL.md §4](https://github.com/FireWall-code/Resonance-for-Sound-Connect/blob/main/docs/PROTOCOL.md)
- overheard models commands/enums/function types as Rust (`mdr-proto` crate: `cmd.rs`, `enums.rs`, `function_type.rs`, `command_name.rs`) but is early (0.1.0) and verified only on WF-C700N + WH-1000XM6. — [overheard repo](https://github.com/andreabedini/overheard)

### Ranking (completeness of v2 table incl. table 2)
1. mos9527 libmdr — generated, all 4 tables, ~150 v2t1 opcodes + full v2t2 (MIT).
2. Resonance PROTOCOL.md — best prose, documents T1 and T2 groups with tested opcodes (PolyForm NC docs).
3. overheard mdr-proto — typed Rust, growing, T1-focused (MIT/Apache).
4. Device Center sony-protocol — hand-coded V1/V2, capability-driven, feature-oriented not exhaustive (MIT).
5. Gadgetbridge PayloadTypeV2 — most-tested but smallest; T1 only, no 0x0E (AGPL).
6. AndreasOlofsson/mdr-protocol (2021) + ohm-app (2023) — historical/partial.

### Gaps
- No project claims a *verified* exhaustive table-2 opcode list for a specific model; mos9527's T2 is generated from the app but per-model which T2 functions are answered is only known where someone captured it.

## Key question 3: Hidden/undocumented capabilities already found (accepted by hardware but hidden or absent in Sound Connect)

### Takeaway
Several categories are documented. The strongest evidence: (a) commands enabled for other models that a given model still answers (Resonance notes the XM6 answers connection-mode `E7` it doesn't declare); (b) test/factory modes present in the protocol (NC test mode, face-tap test mode, call test sound, earbud-fit detection, factory reset, reboot, power-off) that Sound Connect only surfaces contextually; (c) raw/underlying settings the app gates behind UI logic (e.g. Background Music that the app lets you crash the headphones with — see the XM6 reboot bug); (d) custom voice-guidance packs (fully reverse-engineered and installable from a PC); (e) firmware readout and action logs. "Hidden LDAC-switching on a model that negotiates AAC" is NOT a headphone-side command — it is host-stack-limited (see Q4). There is no evidence of a secret "developer unlock."

### Cited Findings — settings a model answers but the app hides/doesn't declare
- Resonance: the XM6 "answers `02` [connection mode] while only declaring `E7`" — i.e. the device responds to a capability it does not advertise. Also: Cinema mode (`E8 04`) is "accepted without effect or notification; the XM6 does not declare function `E5`." Sony voice assistant (`34`) is "refused until it has been set up from the phone." — [Resonance PROTOCOL.md §4b, §5](https://github.com/FireWall-code/Resonance-for-Sound-Connect/blob/main/docs/PROTOCOL.md)
- hush: on the WH-1000XM6 the ambient-sound sub-type Gadgetbridge uses (`0x15`/`0x17`) gets no reply or a stale one; the sub-type that round-trips is `0x19`. So the correct opcode for a model can differ from what other clients send — found by probing. — [hush README](https://github.com/ismoilovdevml/hush)
- Device Center issue #13: "The codec shown in the UI is hardcoded to LDAC" — codec readout exists on the wire (opcode `0x12`/`0x13`) but the app didn't read it; fixed by actually querying. — [Device Center #13](https://github.com/marconvcm/sony-device-center/issues/13)

### Cited Findings — test / factory / debug modes in the protocol
- libmdr enums expose: `GET_TEST=0x0F`, `NcTestModeOperation` (TEST_MODE_START/FINISH), `FaceTapTestModeOperation` (START/FINISH), `CallSettingsTestSoundControl` (START), `EarpieceFittingDetectionOperation` (DETECTION_START / CANCEL / START_FORCEFUL), `ResetType.FACTORY_RESET`, `SystemInquiredType.FACE_TAP_TEST_MODE=0x0B`, `HEAD_GESTURE_TRAINING=0x10`. These are protocol-level test/calibration entry points, not normally exposed as free-standing UI. — [ProtocolV2T1.hpp](https://github.com/mos9527/SonyHeadphonesClient/blob/v1-compat/libmdr/include/mdr/Generated/ProtocolV2T1.hpp)
- Gadgetbridge builds concrete "dangerous" frames: factory reset = `0xf8 09 01` (COMMAND_1), reboot = `0x98 00 16 01`, power-set `0x24`. These work but are destructive. — [SonyProtocolImplV2.java](https://codeberg.org/Freeyourgadget/Gadgetbridge/src/branch/master/app/src/main/java/nodomain/freeyourgadget/gadgetbridge/service/devices/sony/headphones/protocol/impl/v2/SonyProtocolImplV2.java)
- Earbud fit test is documented end-to-end by Resonance (`F4 06 … / F8 06 …` with progress `F9 06` and result `FD 06`). — [Resonance PROTOCOL.md §4](https://github.com/FireWall-code/Resonance-for-Sound-Connect/blob/main/docs/PROTOCOL.md)

### Cited Findings — raw EQ, battery, firmware, logs, paired-device management
- Raw 10-band EQ beyond the UI: hush and Resonance both drive the device's self-described EQ (`0x50 00 01` returns band/step/preset counts; `0x5A 00` returns the 10 centre frequencies 31 Hz–16 kHz; manual curve set with `0x58 00 A0 0A <10 bands>`), which Gadgetbridge's 5-band+Clear-Bass decoder does not fit. So a new client can expose the true band layout the app abstracts. — [hush README](https://github.com/ismoilovdevml/hush), [Device Center #10](https://github.com/marconvcm/sony-device-center/issues/10)
- Firmware/model/serial readout: `04 01`/`04 02` (model/firmware), `02 00` (MAC address) are device-answered. — [Resonance PROTOCOL.md §4](https://github.com/FireWall-code/Resonance-for-Sound-Connect/blob/main/docs/PROTOCOL.md)
- Action/operation logs: the device pushes `C9 …` (action log) unsolicited; `LogInquiredType` has ACTION_LOG, TIME_SERIES_OPERATION_LOG, SOUND_DROPOUT notifiers — data the app consumes internally but never shows the user. Resonance decodes the safe-listening `55 xx` logs (per-earbud u32 timestamp, level, u32 total) but not the WHO-dose % conversion (computed by the phone app). — [Resonance PROTOCOL.md §5, §6](https://github.com/FireWall-code/Resonance-for-Sound-Connect/blob/main/docs/PROTOCOL.md), [ProtocolV2T1.hpp](https://github.com/mos9527/SonyHeadphonesClient/blob/v1-compat/libmdr/include/mdr/Generated/ProtocolV2T1.hpp)
- Paired-device management over table 2: list remembered devices (`36 02`), connect/disconnect/forget (`3C 02`), switch audio source (`3C 01`), enter pairing mode (`34 02 01 00`) — a full multipoint broker that the desktop app ecosystem mostly doesn't expose. — [Resonance PROTOCOL.md §4](https://github.com/FireWall-code/Resonance-for-Sound-Connect/blob/main/docs/PROTOCOL.md)

### Cited Findings — custom voice-guidance packs (confirmed, PC-installable)
- fix-whxm4-voice replaces the WH-1000XM4 voice prompts with your own audio by building a custom voice pack and uploading it from a PC, replaying exactly the Sound Connect update sequence (MDR "language update mode" on/off over the Sony control channel + Airoha RACE FOTA over channel 21). No firmware is modified; the headphones verify and install the pack themselves. Tested on firmware 3.0.1. MIT. — [fix-whxm4-voice README](https://github.com/aaron-p1/fix-whxm4-voice), [ADR 0001](https://github.com/aaron-p1/fix-whxm4-voice/blob/main/docs/adr/0001-direct-bluetooth-upload.md)
- HelgeSverre/sony-vp-extract decrypts and extracts the voice-guidance MP3 prompts from Sony's CDN `.bin` packs (54 prompts × 10 languages, downloadable from `info.update.sony.net/HP002/VGIDLPB04xx/...`). The AES-128-CBC key was recovered by dumping the Airoha MT2811 firmware over BLE RACE and disassembling the FOTA decryption routine. MIT. — [sony-vp-extract README](https://github.com/HelgeSverre/sony-vp-extract), [WRITEUP.md](https://github.com/HelgeSverre/sony-vp-extract/blob/main/docs/WRITEUP.md)

### Inferences
- "Hidden capability" splits cleanly into (1) opcodes the firmware answers but the app hides/mis-sends (safely exploitable: codec readout, raw EQ, action logs, test modes, paired-device broker, battery-care/caring-charge/stamina/BT-standby which appear in `PowerInquiredType`) and (2) things that require the Airoha RACE layer, not MDR (voice packs, firmware, RAM/flash). A new MDR library can own category 1 fully; category 2 needs a second transport.
- No credible evidence of a Sony "developer/factory unlock code"; the SEO article claiming Reddit-confirmed hidden features is low quality and unsourced. The real "hidden" surface is the undeclared-but-answered opcodes plus the test modes.

### Gaps
- No catalogue exists of exactly which per-model "enabled for other models" settings each model silently accepts; it is discovered ad hoc (Resonance's XM6 `E7`/`02` note is the clearest single example).
- Battery *cycle count* specifically: not found as a documented opcode in any source; `PowerInquiredType` has battery/caring-charge/safe-mode but no cycle-count entry surfaced. (Gap.)

## Key question 4: Host-side features that are feasible without new firmware commands, and what the community has asked for

### Takeaway
The firmware only answers commands it implements, so genuinely new capabilities beyond the opcode set must live host-side. The most-requested, clearly feasible-without-new-opcodes items are: a CLI/hotkey/automation interface, auto-connect/ownership brokering, battery history, and per-context scenes. Several are already partly built (hush CLI, overheard daemon+D-Bus+scripts, Device Center daemon/IPC).

### Cited Findings — requested host-side features
- CLI for automation and keybinds — mos9527 #15: "a concrete use case… being able to automatically toggle ambient mode whenever I hit the pause/resume button." Maintainer: CLI / bindings "has been in the works… possibly in a separate project utilizing the now standardized protocol library (libmdr)." — [mos9527 #15](https://github.com/mos9527/SonyHeadphonesClient/issues/15)
- Already shipped host-side: hush ships a `hush` CLI ("everything the panel does… useful for scripts, hotkeys and Shortcuts"), talks to the running app over a unix socket so only one process holds the single RFCOMM channel. — [hush README](https://github.com/ismoilovdevml/hush)
- overheard is a daemon + D-Bus + CLI + GNOME Shell tile + GTK app; it feeds each earbud's battery to BlueZ as `org.bluez.BatteryProvider1` (native OS battery UI) and sends low-battery desktop notifications — host-side features Sony never offered. — [overheard README](https://github.com/andreabedini/overheard)
- Auto-connect / ownership broker — Device Center lists as remaining debt: "Add a per-device process lock or an ownership broker before claiming global exclusion"; the single RFCOMM channel means direct GUI, daemon, and third-party software compete for it. Pairing-mode hold-off is also an open problem (auto-reconnect races the user's attempt to enter pairing mode). — [Device Center technical-debt.md](https://github.com/marconvcm/sony-device-center/blob/main/docs/technical-debt.md)
- Gadgetbridge issue inventory of "not possible to implement / app-dependent" for XM5 clarifies the host-side frontier: adaptive sound control (phone detects activity/location and pushes settings), scene-based listening, auto-switch multipoint (needs compatible speaker), Sound AR — all of these are *host-side logic the phone app performs*, not headphone opcodes, so a desktop broker could reimplement them. — [Gadgetbridge #5934](https://codeberg.org/Freeyourgadget/Gadgetbridge/issues/5934)
- joserebelo (GB maintainer): the "Bluetooth connection quality" toggle "is effectively selecting the audio codec, which we do not support right now" — i.e. codec/connection-priority switching IS an opcode (`E6/E8 02`), feasible, just unimplemented there. — [Gadgetbridge #5934](https://codeberg.org/Freeyourgadget/Gadgetbridge/issues/5934)

### Inferences (feasible host-side, no new firmware opcodes)
- Automation scenes, per-app ambient, auto-switch multipoint on audio focus, CLI/hotkeys, battery history logging, and an auto-connect broker are all achievable by composing existing MDR opcodes with host-side state/policy. The adaptive-sound-control feature the phone app brands is exactly this pattern (sensor/context on the host → choose an NC/ASM opcode), so a desktop version is feasible using host sensors (foreground app, location, time).
- The hard constraint everyone hits is the single control connection (one RFCOMM/accessory session per host), which is why a broker/daemon is the right architecture — confirmed by hush (unix socket), overheard (daemon owns channel), Device Center (sonyd), and mos9527's iOS note.

### Gaps
- No shipped desktop client yet implements full automation "scenes" or per-app ambient; they are requested/architecturally anticipated but not delivered as of 2026-11-07.

## Key question 5: Firmware update path — has anyone reverse-engineered Sony's headphone firmware format/protocol?

### Takeaway
Yes, extensively — but the firmware itself is Airoha (MediaTek-subsidiary) silicon, so the "firmware" work is Airoha RACE/FOTA, not Sony MDR. Sony's control channel only toggles "update mode"; the actual transfer is the Airoha FOTA sequence over a separate RFCOMM channel (UUID `8901dfa8-…`, often channel 21) or BLE RACE. Official Sony firmware images are downloadable, their container format is parsed, and the per-model AES-128-CBC keys needed to decrypt them have been recovered by dumping flash over RACE. Flashing (incl. downgrade) and custom voice packs are device-verified; stray RACE writes outside the FOTA partition are reported to brick devices.

### Cited Findings — the FOTA container and keys
- ramikg/airoha-firmware-parser: an 010-Editor template + Python decryptor for the Airoha firmware format used by "numerous Sony headphones (notably WH-1000XM4 and WH-1000XM5, whose MediaTek chips are rebranded Airoha chips)." Decryptor is AES with a key/IV; `--no-decompress`, `--no-decrypt`, `--reverse-key-and-iv` flags. Unlicense. — [airoha-firmware-parser](https://github.com/ramikg/airoha-firmware-parser)
- The Airoha UPG package is TLV-structured: BASIC_INFO (compression type None/Lzma/LzmaAes, integrity Crc32/Sha256/Sha256Rsa, firmware offset/size), MOVER_INFO (section table: source offset, decompressed size, flash dest offset), VERSION_INFO, INTEGRITY_VERIFY_INFO (SHA-256 per section), DEVICE_NAME/TYPE, IS_NVDM_INCOMPATIBLE_FLAG; file starts with a 32-byte SHA-256 over bytes 0x100–EOF. mos9527 ported the parser to an ImHex template. — [mos9527 discussion #45](https://github.com/mos9527/SonyHeadphonesClient/discussions/45)
- mos9527 discussion #45 ("Airoha Firmware Decryption for XM4/5/6 devices (Custom Voicepack, etc)") documents the method: brute-force LZMA headers against a flash dump to recover the AES KEY/IV pair, then use ramikg's decryptor (with `--reverse-key-and-iv`). It tabulates recovered KEY/IV pairs for WH-1000XM6, WF-1000XM5, WH-1000XM4. Official firmware can be downloaded from the MDR_Proxy mirror. (The discussion reproduces the actual key bytes; a new project should treat those as encumbered and not redistribute them.) — [mos9527 discussion #45](https://github.com/mos9527/SonyHeadphonesClient/discussions/45)
- sony-vp-extract WRITEUP: WH-1000XM4 = Airoha MT2811 (Cortex-M4); RACE is exposed over BLE GATT (service `dc405470-a351-4a59-97d8-2e2e3b207fbb`, TX `bfd869fa-…`, RX `2a6b6575-…`); `RACE_STORAGE_PAGE_READ` (0x0403) reads 256-byte flash pages, `RACE_READ_ADDRESS` (0x1680) reads 4 bytes of RAM (~15/s). Flash partition table: bootloader 0x08001000, CM4 firmware 0x08002000 (64 KB), NVDM 0x08012000 (128 KB), FOTA 0x081B9000 (2 MB), external flash / voice guidance 0x0C510000 (6 MB). The AES key lives in `.rodata`; found by tracing the FOTA decryption path. — [sony-vp-extract WRITEUP.md](https://github.com/HelgeSverre/sony-vp-extract/blob/main/docs/WRITEUP.md)

### Cited Findings — the flashing protocol and firmware mirrors
- lzghzr/MDR_Proxy (MIT, 461★, created 2019, pushed 2026-11-05): a local MITM proxy that intercepts Sound Connect's firmware download/update so you can side-grade/downgrade; its appendix mirrors official firmware per model (categoryID HP001/HP002 + serviceID, e.g. WH-1000XM4 = HP002/2943, WH-1000XM6 = HP002/2984, WF-1000XM6 = 2985) from Sony's `info.update.sony.net`. The README warns MITM/cert-import use is at your own risk. — [MDR_Proxy](https://github.com/lzghzr/MDR_Proxy)
- randwardatake/wh1000xm4-anc-optimizer (GPL-3.0, 58★) device-verifies the full Airoha FOTA flash over Bluetooth for the WH-1000XM4: it documents SDP channels (MDR control via UUID `96cc203e-…`, RACE/`Airoha_APP` via UUID `8901dfa8-…`), the RACE header (`<BBHH`: head 0x05/0x15, type 0x5A cmd/0x5B resp/0x5C no-resp/0x5D indication, length, cmd_id), flash opcodes (0x0403 read, 0x0402 program with CRC-8 Maxim page checksum bit-reversed, 0x0404 erase, 0x1C00 partition info, 0x1C01 integrity check, 0x1C02 commit), RAM read/write (0x1680/0x1681), and the ATCI tunnel (0x0F92, dead on retail fw). It device-verified downgrade 3.0.1→2.5.0 and back. — [wh1000xm4-anc-optimizer README](https://github.com/randwardatake/wh1000xm4-anc-optimizer), [WIRE_PROTOCOLS.md](https://github.com/randwardatake/wh1000xm4-anc-optimizer/blob/main/docs/WIRE_PROTOCOLS.md), [STATUS.md](https://github.com/randwardatake/wh1000xm4-anc-optimizer/blob/main/docs/STATUS.md)
- fix-whxm4-voice reverse-engineered the exact app FOTA order from jadx (Sound Connect 12.4.2): MDR "language update mode" ENABLE → RACE chip-name NV read 0x0A00 → FOTA info queries (0x1C08/0x1C1C/0x1C00/0x1C04) → erase (0x0404) / program (0x0402) / integrity (0x1C01) → MDR update mode DISABLE → re-ENABLE + commit (0x1C02); the link dropping is treated as success. The pack `.bin` is written verbatim into the FOTA partition at the device-reported address; the device unpacks/installs itself. FOTA is over Bluetooth Classic RFCOMM for this chip, not BLE. — [fix-whxm4-voice upload-protocol.md](https://github.com/aaron-p1/fix-whxm4-voice/blob/main/docs/upload-protocol.md)
- The Airoha FOTA/RACE layer is also the subject of published security research (ERNW, full disclosure 39C3, 2025-12-27): CVE-2025-20700 (BLE GATT reachable unpaired), CVE-2025-20701 (Classic pairing bypass), CVE-2025-20702 (RACE unauthenticated read/write of RAM and flash). Affected Sony models listed include WH-1000XM4/5/6, WF-1000XM3/4/5, LinkBuds S, ULT Wear, WH-CH520, WH-CH720N, WH-XB910N, WI-C100, WF-C500/C510. Flash writes are restricted to the FOTA partition, but the symmetric keys can be read from flash and used to encrypt a modified image; RFCOMM flashing takes ~3–5 min. auracast-research/race-toolkit (493★, no license declared) implements RAM/flash dump, device info, and preliminary FOTA over BLE/RFCOMM/USB-HID. — [insinuator.net / ERNW disclosure](https://insinuator.net/2025/12/bluetooth-headphone-jacking-full-disclosure-of-airoha-race-vulnerabilities), [race-toolkit](https://github.com/auracast-research/race-toolkit)
- mos9527's own `UPDT_*` / `TandemFota*` structs (ENTER/EXIT_FW_UPDATE_MODE, START/FINISH/CANCEL_TRANSFER, EXECUTE_FW_UPDATE; UPDT_TRANSFER_DATA with offset+data; Tandem result/status enums) show the MDR-side firmware-update opcodes are fully modelled in libmdr even though the client doesn't implement flashing. — [ProtocolV2T1.hpp](https://github.com/mos9527/SonyHeadphonesClient/blob/v1-compat/libmdr/include/mdr/Generated/ProtocolV2T1.hpp)

### Inferences
- A new library that wants firmware/voice-pack/NVDM features must implement a second transport (Airoha RACE over the `8901dfa8-…` SPP channel or BLE GATT), separate from MDR. MDR only flips "update mode." This is a meaningfully larger, riskier undertaking than MDR control.
- Because official images + container parser + per-model keys are all public, building a cross-platform downgrade/custom-voice/NVDM-backup tool is feasible today, but it is Airoha-specific and model-specific.

### Gaps
- No evidence of running fully *custom* (non-Sony-signed) firmware; integrity/signature checks (0x1C01, possibly RSA-2048 vs eFuses — "Unverified" per xm4-optimizer STATUS) gate it. Only official signed images and self-unpacked voice packs are device-verified.

## Key question 6: Which existing codebase is the best foundation to port or learn from?

### Takeaway
For a new permissive/proprietary library, mos9527 libmdr is the best technical foundation: MIT, C++20, fully data-/codegen-driven for all four tables, with a C ABI, replay tests, and the IR to regenerate tables from the app. For a Rust greenfield, overheard (MIT/Apache, sans-IO) is the cleanest architecture to learn from. Gadgetbridge is the most battle-tested but is AGPL (copyleft — a hard constraint for a proprietary library) and table-1 only. Device Center (MIT, C++) is a good mid-size, capability-driven reference. Resonance docs (PolyForm NC) and ohm-app docs (CC0) are references, not code to port — and PolyForm NC forbids commercial use.

### Cited Findings — structure, extensibility, tests, codegen, license
- mos9527 libmdr — MIT, C++20 (GCC14/Clang21/MSVC19), CMake 3.31+. Payload structs are data-driven: each struct's first field is a `Command` enum defaulting to its opcode; trivially-serializable PODs use `MDR_DEFINE_TRIVIAL_SERIALIZATION` (packed, memcpy), dynamic ones use `MDR_DEFINE_EXTERN_SERIALIZATION` with codegen-generated Serialize/Deserialize/Validate; `// CODEGEN` comments drive validation (EnumRange, Range, Field, Ignore). Codegen tools (`tooling/*Codegen.cpp`) require LLVM/libclang and run via `cmake --build --target mdr_codegen`. Extending with a new opcode = add the enum value + struct with CODEGEN hints, regenerate. Has a stable C ABI (`MDR_ABI_VERSION`), optional C++ exceptions-off build, non-blocking polled IO via an `MDRConnection` vtable (so the protocol core is transport-agnostic), and replay tests (`mdr_replay_tests` over captured `.bin` fixtures, run in CI). Also ships bindings/targets for Windows/macOS/Linux/Android/iOS/Web(Emscripten)/OpenHarmony. — [DEVELOPER.md](https://github.com/mos9527/SonyHeadphonesClient/blob/v1-compat/DEVELOPER.md), [tests/README.md](https://github.com/mos9527/SonyHeadphonesClient/blob/v1-compat/tests/README.md)
- Gadgetbridge — AGPL-3.0, Java. Hand-coded `PayloadTypeV1/V2` enums + `SonyProtocolImplV1/V2`; broadest tested model coverage and the de-facto byte-layout reference everyone cites, but table-1 only for v2 and many "not implemented for V2" stubs. AGPL means any derived library (even network-served) must be AGPL — unsuitable for a permissive or proprietary library; use it to learn, not to copy code. — [SonyProtocolImplV2.java](https://codeberg.org/Freeyourgadget/Gadgetbridge/src/branch/master/app/src/main/java/nodomain/freeyourgadget/gadgetbridge/service/devices/sony/headphones/protocol/impl/v2/SonyProtocolImplV2.java)
- overheard — dual MIT/Apache-2.0, Rust, sans-IO. Workspace of small crates: `mdr-frame` (framing + stop-and-wait ARQ, `no_std`+alloc), `mdr-proto` (typed commands/codecs, `no_std`+alloc), `mdr-session` (sans-IO state machine: handshake, ARQ, request/reply correlation, capability+state caching), `mdr-smol` (async client), `overheard-transport` (RFCOMM/SPP + BLE/GATT). Capability-gated, not model-gated. Early (0.1.0), verified on WF-C700N + WH-1000XM6. Best architecture to learn from for a clean new library; permissive license. — [overheard README](https://github.com/andreabedini/overheard)
- Device Center sony-protocol — MIT, C++. `libs/sony-protocol` with `IProtocol`, `ProtocolV1`/`ProtocolV2`, `FrameCodec`, `CapabilityDiscovery`/`CapabilityCache`, `DeviceProfileRegistry`. Hand-coded but cleanly capability-driven (e.g. `ProtocolV2(tenBandEqualizer, noiseControlLayout, detailedBattery)` selects wire variants from a model profile). Uses vendored nlohmann/json. Daemon/IPC architecture (sonyd + sonyctl + Qt GUI). Good mid-size permissive reference; feature-oriented, not an exhaustive table. — [ProtocolV2.h](https://github.com/marconvcm/sony-device-center/blob/main/libs/sony-protocol/include/sony/protocol/ProtocolV2.h), [technical-debt.md](https://github.com/marconvcm/sony-device-center/blob/main/docs/technical-debt.md)
- Resonance — PolyForm Noncommercial License 1.0.0 (code) + docs. Best prose protocol doc with evidence levels, incl. table 2. License forbids commercial use and even contributions are licensable by the author "in paid versions"; docs are a reference, not something to port into a permissive/commercial library. C#/.NET 10, WPF. — [Resonance LICENSE](https://github.com/FireWall-code/Resonance-for-Sound-Connect/blob/main/LICENSE), [CONTRIBUTING.md](https://github.com/FireWall-code/Resonance-for-Sound-Connect/blob/main/CONTRIBUTING.md)
- ohm-app/sony-headphones-bluetooth-documentation — CC0-1.0 (public domain), last pushed 2024-01-11. Documents the RFCOMM/L2CAP framing only (header/length/FCS, EA field); partial and dated. Safe to reuse (CC0) but thin. — [ohm-app spec](https://github.com/ohm-app/sony-headphones-bluetooth-documentation/blob/main/docs/Protocol/Specification.md)
- AndreasOlofsson/mdr-protocol — docs (2021), the canonical early writeup of Tandem framing/DataTypes/seq/ACK/checksum; good for learning the transport, superseded for tables. — [mdr-protocol](https://github.com/AndreasOlofsson/mdr-protocol)

### Recommendation (inference)
- New permissive/proprietary library, C/C++: fork or vendor mos9527 libmdr (MIT), seed tables from its `tooling/ida/generated/*.json`, keep its codegen so new opcodes stay data-driven. New Rust library: model it on overheard's sans-IO crate split. In both cases, use Gadgetbridge and Resonance only as behavioural references (license incompatibility for Gadgetbridge/Resonance; CC0 ohm-app and AndreasOlofsson are freely reusable but thin).

### Gaps
- No head-to-head benchmark of per-model correctness across these libraries exists; "most tested" (Gadgetbridge) vs "most complete" (libmdr) is a license/architecture trade-off, not a measured accuracy one.

## Key question 7: Legal/safety — risks of undocumented commands; DMCA/EULA stance in the projects' own words

### Takeaway
Bricking risk from pure MDR control commands is low but non-zero (one documented case of a command sequence crashing/rebooting the XM6; destructive opcodes like factory reset/reboot/power-off are real), while Airoha RACE flash writes outside the FOTA partition are reported to brick devices. Every project disclaims Sony affiliation and frames the work as interoperability/research; the firmware/voice-pack projects add explicit at-your-own-risk warnings and refuse writes outside known-safe partitions. None cites a DMCA action; several document decompilation openly.

### Cited Findings — bricking / crash reports
- XM6 crash from an MDR control command: enabling Background Music while voice commands are on makes the WH-1000XM6 "crash shortly after applying the mode… go off, and then turn on again" and revert the setting; the maintainer reproduced it. Cause: the client set a mode the device reports as blocked; fix is to honour the capability/blocked codes. This is a reboot/crash, not a permanent brick. — [mos9527 #76](https://github.com/mos9527/SonyHeadphonesClient/issues/76)
- Destructive opcodes are live and easy to hit by mistake: hush refuses to transmit outside an allow-list because "a wrong opcode on protocol v2 is not harmless: `0xF8` is `AUTOMATIC_POWER_OFF_BUTTON_MODE_SET` on v1 but **`FACTORY_RESET_SET`** on v2." Its never-sent list: `F8` factory reset, `98` reboot, `24` power off, `2D` firmware transfer, `C4` JSON dump; `hush raw` enforces the same allow-list. — [hush README](https://github.com/ismoilovdevml/hush)
- Airoha RACE write risk: fix-whxm4-voice ADR 0001 — "stray RACE flash writes are known to brick devices," so the tool "refuses any erase or write outside the FOTA partition the headphones report," sends only the app's commands in the app's order, and only accepts a pack that passed a full unpack/check round trip. SAFETY rationale: the voice pack goes to a staging area and the headphones verify/install themselves, "so I don't really see a reason for them to brick." — [fix-whxm4-voice ADR 0001](https://github.com/aaron-p1/fix-whxm4-voice/blob/main/docs/adr/0001-direct-bluetooth-upload.md), [README](https://github.com/aaron-p1/fix-whxm4-voice)
- xm4-optimizer disables write paths on real hardware by default: it "refuses `inject` and `rollback` on real hardware unless `--allow-unverified-write`", refuses firmware files whose SHA-256 isn't one of five known official images unless `--allow-unknown-firmware`, and grades every claim by evidence (device-verified / user-reported / simulation / unverified / contradicted). Its RACE NVDM write (0x0E02) and WRITE_ADDRESS (0x1681) are "non-functional"/"unverified"; "Brick risk is 'none' with official firmware" is itself graded **Unverified**. — [xm4-optimizer STATUS.md](https://github.com/randwardatake/wh1000xm4-anc-optimizer/blob/main/docs/STATUS.md)
- The 2019 MDR_Proxy Reddit thread for WH-1000XM3 firmware flashing carried "This could brick/damage your device, DO IT AT YOUR OWN RISK!" (secondary source; original thread not directly fetched). — [WebSearch result citing the r/sony MDR_Proxy thread](https://www.reddit.com/r/sony/comments/dpsmsq/wh1000xm3_custom_firmware_flash_mdr_proxy/)

### Cited Findings — EULA / DMCA / decompilation stance in projects' own words
- Resonance states: no Sony code is reproduced, "this document only describes bytes on the wire"; CONTRIBUTING: "Never commit code, images or text copied from Sony's apps." — [Resonance PROTOCOL.md](https://github.com/FireWall-code/Resonance-for-Sound-Connect/blob/main/docs/PROTOCOL.md), [CONTRIBUTING.md](https://github.com/FireWall-code/Resonance-for-Sound-Connect/blob/main/CONTRIBUTING.md)
- mos9527 `tooling/ida/README.md`: "Obtain the Sound Connect iOS application through an account and device you are authorized to use… Raw application binaries, IPAs, and IDA databases are local inputs and must not be committed." (i.e. authorship from authorized binaries; generated IR, not Sony's bytes, is committed). — [tooling/ida/README.md](https://github.com/mos9527/SonyHeadphonesClient/blob/v1-compat/tooling/ida/README.md)
- fix-whxm4-voice documents decompiling the signed Sony APK with `jadx --no-res` and records the signing certificate; it frames the work as replaying the app's own procedure for interoperability. sony-vp-extract: "Everything described here was done on my own paired headphones… No authentication mechanisms were bypassed on remote servers." — [upload-protocol.md](https://github.com/aaron-p1/fix-whxm4-voice/blob/main/docs/upload-protocol.md), [sony-vp-extract WRITEUP.md](https://github.com/HelgeSverre/sony-vp-extract/blob/main/docs/WRITEUP.md)
- Every project disclaims affiliation ("not affiliated with or endorsed by Sony"; trademarks acknowledged) — hush, overheard, Resonance, xm4-optimizer, Plutoberth. — [hush README](https://github.com/ismoilovdevml/hush), [overheard README](https://github.com/andreabedini/overheard)

### Inferences
- Practical safety rules for a new library: (1) gate every write behind a model's declared capability from the `06/07` handshake; (2) honour "blocked" status codes before sending a SET; (3) keep a hard allow/deny list for destructive opcodes (F8/98/24/2D/C4) as hush does; (4) treat any Airoha RACE write as high-risk and confine it to the device-reported FOTA partition. The one confirmed "damage" vector from MDR alone is a crash/reboot, recoverable; permanent bricks are associated with RACE flash writes.
- Legal posture that the projects share: author from binaries you're authorized to use, publish derived facts/IR not Sony's code/assets, describe "bytes on the wire," disclaim affiliation. No project reports a takedown; Plutoberth was archived by its owner (not via DMCA).

### Gaps
- No lawyer-reviewed statement on DMCA §1201 / EULA anti-reverse-engineering clauses specific to Sound Connect was found in any project; the stance is practical self-policing, not legal analysis.
- No systematic list of which opcodes are destructive beyond the hush allow/deny list and the obvious factory-reset/reboot/power-off/firmware/JSON-dump set.
