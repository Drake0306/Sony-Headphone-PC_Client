# Sony headphone control protocol (MDR / "Tandem") and reusable libraries — landscape as of 2026-11-06

Scope: the proprietary protocol Sony's "Headphones Connect" (renamed "Sound Connect" in October 2024) app speaks to headphones over Bluetooth Classic RFCOMM/SPP; its documentation, reusable implementations, platform Bluetooth stacks, model coverage, and legal context. All repository metadata (stars, last push, license) was pulled from the GitHub API on 2026-11-06 unless stated otherwise; Gadgetbridge source was read from the Codeberg `master` branch on the same date.

## Key question 1: Where is the protocol documented?

### Takeaway
There is no single canonical spec. The de-facto reference is the Gadgetbridge Java source (AGPL-3.0) on Codeberg, which nearly every 2025–2026 desktop client cites as its byte-layout source; the only prose/standalone docs are small, partial and old (AndreasOlofsson/mdr-protocol 2021, ohm-app CC0 docs 2023) plus newer per-project `PROTOCOL.md`/`docs/protocol.md` files inside apps (Resonance, Nullpoint, sonyctl, overheard, hush). Plutoberth's README explicitly says most of the protocol "has to be obtained either statically or dynamically" and has no wiki spec.

### Inferences
- A new client author should treat Gadgetbridge's `SonyProtocolImplV1/V2` + `PayloadTypeV1/V2` as the primary opcode reference, Resonance's PROTOCOL.md as the best prose for v2 "table 2"/capability discovery, and the APK (Sound Connect, package `com.sony.songpal.mdr`) as the ground truth for anything missing — several projects (Resonance, EncoDeck) plainly derive layouts from reading the app.
- Because Gadgetbridge is AGPL-3.0, several MIT projects (Fanxingkeming, hush, marnunez/sonyctl) state they "read but did not copy" it; that is the licensing pattern a new permissive-licensed client would need to follow (see Key question 6).

## Key question 2: Frame format, and how v1 differs from v2 (and which models use which)

### Takeaway
Both generations share one framing layer: `0x3E | type | seq(0/1) | len(u32 BE) | payload | checksum | 0x3C`, with `0x3C/0x3D/0x3E` escaped as `0x3D, (b & 0xEF)`, an 8-bit sum checksum over everything between the markers, and stop-and-wait ARQ where each data frame is ACKed with `seq' = 1 - seq`. "v1" vs "v2" is a different SDP service UUID plus a largely different opcode table (battery, codec, power, ambient-sound inquiry sub-types, EQ layout) and extra "table 2" (type `0x0E`) command families; Gadgetbridge picks the version from the init reply length (4 bytes = v1, 8 bytes = v2).

### Cited Findings
- Gadgetbridge `Message.java`: `MESSAGE_HEADER = 0x3e`, `MESSAGE_TRAILER = 0x3c`, `MESSAGE_ESCAPE = 0x3d`, `MESSAGE_ESCAPE_MASK = 0b11101111` (0xEF); layout comment: header, type, "Sequence Number - needs to be updated with the one sent in the ACK responses", "Payload Length - 4-byte big endian int", payload, "Checksum (1-byte sum, excluding header)"; encode writes header, escaped body, escaped checksum, trailer; decode unescapes, then checks `calcChecksum(messageBytes, 1, len-2)`. — [Message.java](https://codeberg.org/Freeyourgadget/Gadgetbridge/raw/branch/master/app/src/main/java/nodomain/freeyourgadget/gadgetbridge/service/devices/sony/headphones/protocol/Message.java)
- Gadgetbridge `MessageType.java`: `ACK(0x01)`, `COMMAND_1(0x0c)`, `COMMAND_2(0x0e)`. — [MessageType.java](https://codeberg.org/Freeyourgadget/Gadgetbridge/raw/branch/master/app/src/main/java/nodomain/freeyourgadget/gadgetbridge/service/devices/sony/headphones/protocol/MessageType.java)
- AndreasOlofsson/mdr-protocol lists the full DataType byte space: 0x00 Data, 0x01 Ack, 0x02 DataMcNo1, 0x09 DataIcd, 0x0A DataEv, 0x0C DataMdr, 0x0D DataCommon, 0x0E DataMdrNo2, 0x10 Shot, 0x12 ShotMcNo1, 0x19 ShotIcd, 0x1A ShotEv, 0x1C ShotMdr, 0x1D ShotCommon, 0x1E ShotMdrNo2, 0x2D LargeDataCommon; it notes a frame can span several RFCOMM packets and one packet can hold several frames ("treat the link as a byte stream"). — [mdr-protocol](https://github.com/AndreasOlofsson/mdr-protocol)

- Note the opcode collision: `0x22` is POWER_OFF in v1 but BATTERY_LEVEL_REQUEST in v2 — SonyBridge's release notes describe a bug where "a v2 battery request opcode was wrongly sent to v1 headsets." — [SonyBridge releases](https://github.com/AmitRajput-Dev/SonyBridge/releases)
- Resonance's prose model of v2: frame type `0C` = command table 1, `0D` = common, `0E` = command table 2. Table 1 groups: connect `00`, EQ `50`, noise control `60`, general settings `D0`. Table 2 groups: power `20`, peripherals `30`, voice guidance `40`, safe listening `50`, LE Audio `60`, party `70`, system `F0`. On connect `06 00` is sent on both tables; reply `07 00` lists supported functions with priorities, and the UI adapts. v2 encodes on = `00` whereas v1 uses `01` = on. Only one control connection per host at a time. — [Resonance PROTOCOL.md](https://github.com/FireWall-code/Resonance-for-Sound-Connect/blob/main/docs/PROTOCOL.md)
- Fanxingkeming's version detection: the INIT reply is 4 or 8 bytes (v1/v2) and "v2 requires an extra `06 00` handshake step"; sony-ult-ctl: handshake `[0x00,0x00]`, valid v2 reply begins `[0x01,0x00,0x03]`; data type 0x0C for DATA_MDR, 0x01 ACK. — [sony-headphones-control](https://github.com/Fanxingkeming/sony-headphones-control); [sony-ult-ctl](https://github.com/Leonard013/sony-ult-ctl)
- Ambient-sound inquiry sub-types differ per device: Gadgetbridge sends `0x15` (or `0x17` on devices with wind-noise reduction); sony-ult-ctl uses `0x17` on WH-ULT900N (SET, GET 0x66, RET 0x67, NOTIFY 0x69; ambient level 0–20 is the last byte of the 7-byte SET); on WH-1000XM6 (fw 3.1.5) hush reports `0x15` and `0x22` get no reply, `0x17` returns a stale all-zero payload, and only `0x19` round-trips, so hush probes the sub-type and EQ layout at connect. — [hush](https://github.com/ismoilovdevml/hush); [sony-ult-ctl](https://github.com/Leonard013/sony-ult-ctl)
- WH-1000XM6 generation changes (xm6-control, verified on fw 3.x via protocol log): "the equalizer answers a different inquired type, wearing detection moved to the SYSTEM family, and multipoint management lives on the second message table"; EQ presets Off/Heavy/Clear/Hard/Soft/Custom with a ten-band custom curve; listening modes Standard/Background Music (room sizes)/Cinema. mos9527's XM6 doc: only `Heavy/Clear/Hard/Soft (0x30–0x33)`, `Custom (0xA0)` are accepted by the EQ as of FW 3.0.0. Sony Device Center: XM6 uses 10 bands with raw levels 0–12 and no separate Clear Bass. — [xm6-control](https://github.com/ruimartins23/xm6-control); [mos9527 WH-1000XM6.md](https://github.com/mos9527/SonyHeadphonesClient/blob/v1-compat/docs/device-support/WH-1000XM6.md); [sony-device-center](https://github.com/marconvcm/sony-device-center)
- Escape-mask pitfall: hush notes the mask bug "stays invisible for a long time, because most payloads never contain those three bytes"; it surfaced in the EQ band table where 16000 Hz is `0x3E80`. — [hush](https://github.com/ismoilovdevml/hush)
- Which models use which (consolidated): v1 = WH-1000XM2/XM3/XM4, WF-1000XM3, WF-SP800N, WI-SP600N, WH-XB900N, MDR-XB950BT, WI-1000X, MDR-1000X; v2 = WF-1000XM4/XM5/XM6, WH-1000XM5/XM6, LinkBuds, LinkBuds S, WH-CH720N, WH-CH520, WH-XB910N, WH-ULT900N, WF-C500/C510/C700N/C710N, WI-C100. — [Gadgetbridge init comments](https://codeberg.org/Freeyourgadget/Gadgetbridge/raw/branch/master/app/src/main/java/nodomain/freeyourgadget/gadgetbridge/service/devices/sony/headphones/SonyHeadphonesProtocol.java); [sony-device-center model table](https://github.com/marconvcm/sony-device-center); [SonyBridge model list](https://github.com/AmitRajput-Dev/SonyBridge); [gabamnml/omarchy-sony-headphones](https://github.com/gabamnml/omarchy-sony-headphones) ("v1 is used by the over-ear 1000X line up to the XM4")
- Head tracking is a separate protocol, not MDR: sony-head-tracker (MIT-ish, 597 stars, last push 2026-08-28) reads the "Android Head Tracker" HID sensor exposed by Sony headsets (WH-1000XM5 maintainer-tested; XM6 and others community-confirmed; XM4 does not work); the Linux port scans `/dev/hidraw*` for the Sensor page/Custom (`0x20`/`0xE1`) usage and the `#AndroidHeadTracker#` marker. — [sony-head-tracker](https://github.com/NicholasSlattery/sony-head-tracker); [SonyTrackerLinux](https://github.com/kdani3/SonyTrackerLinux)

### Inferences
- Gadgetbridge's `SonyProtocolImplV2 extends SonyProtocolImplV1` design shows v2 is best modelled as "v1 framing + overridden opcode table + extra families," not a new protocol; a new implementation should put the version switch at the opcode-table layer and keep one framer/ARQ engine.
- Because sub-types and EQ layouts vary even within v2 (XM6 vs ULT WEAR vs XM5), a robust client needs runtime capability discovery (the `06 00` / `07 00` supported-function list) and probing rather than a static per-model table; hush and mos9527 both moved in that direction.
- The Sony Device Center UUIDs are most likely a README/transcription error (or a fetch artefact); use the Gadgetbridge values.

### Gaps
- No source fully enumerates the `07 00` supported-function list format or the table-2 opcode values; Resonance's PROTOCOL.md and Gadgetbridge's `SYSTEM_CONTROL`/`SERVICE_LINK` entries are the closest.
- The Airoha RACE side-channel mentioned by overheard (and the "Airoha chipset" note in sony-ult-ctl) was not documented in any fetched page beyond its existence.
- LE Audio/GATT control: EncoDeck claims XM6 LE Audio control (handshake, battery, NC) was verified over BLE by a contributor, and overheard's transport supports BLE/GATT with the XM6 GATT path "needing a hardware report," while Resonance says LE Audio is "not implemented" and that switching drops the Classic control link. No documented GATT UUIDs were found.

## Key question 3: Reusable libraries and SDKs (any language)

### Takeaway
Nothing is published on PyPI, crates.io, npm, pub.dev or NuGet as a Sony-headphone protocol library; every reusable piece is an in-repo module of an app. The most library-shaped options are: Gadgetbridge's Java implementation (AGPL-3.0, broadest model coverage, Android-only transport); mos9527/SonyHeadphonesClient's `libmdr` (C++20, MIT, platform-agnostic, V1+V2, with a `libmdr-bt` backend layer for Windows/Linux/macOS/iOS/Emscripten) — already reused by at least four other projects (Lauscher, aResiy/sony-control, abhiinhii/sony-tray, Nullpoint); Sony Device Center's `sony-protocol`/`sony-transport`/`sony-core` C++20 libs (MIT); overheard's sans-IO Rust crates (MIT/Apache-2.0, early); and Nullpoint's TypeScript `core` package (Apache-2.0).

## Key question 4: Bluetooth RFCOMM/SPP access per desktop platform, and cross-platform wrappers

### Takeaway
Every platform has a native RFCOMM client API usable by a desktop app — Windows Winsock (`AF_BTH`/`BTHPROTO_RFCOMM`, SDP lookup by `serviceClassId`) or WinRT `RfcommDeviceService`; macOS IOBluetooth (`IOBluetoothDevice.openRFCOMMChannelSync/Async`, main-thread-bound delegates; `com.apple.security.device.bluetooth` entitlement if sandboxed); Linux BlueZ (`AF_BLUETOOTH`/`BTPROTO_RFCOMM` sockets or D-Bus Profile API, `bluer` crate). Cross-platform wrappers exist but are thin and unevenly verified: 32feet.NET (.NET), `bluetooth_rfcomm` (Dart), `bluetooth-serial-port` (Node); every Sony client surveyed wrote its own per-OS backend instead. A device-side constraint shapes all designs: Sony headsets accept only one control-channel connection at a time.

### Cited Findings
- **Windows / WinRT**: `Windows.Devices.Bluetooth.Rfcomm.RfcommDeviceService` "Represents an instance of a service on a Bluetooth BR device", introduced Windows 10 build 10240, requires the `bluetooth` app capability; `GetDeviceSelectorForBluetoothDeviceAndServiceId(BluetoothDevice, RfcommServiceId)` (1607+), `FromIdAsync`, `RequestAccessAsync` ("invokes Device Consent and must be called on the UI thread ... paired devices do [require consent]"), `GetSdpRawAttributesAsync`; connect with `StreamSocket` to `ConnectionHostName`/`ConnectionServiceName`. — [RfcommDeviceService docs (updated 2025-11-21)](https://learn.microsoft.com/en-us/uwp/api/windows.devices.bluetooth.rfcomm.rfcommdeviceservice)
- **Windows / Winsock**: `connect()` with `SOCKADDR_BTH`; either set `port` to a known RFCOMM channel (requires the app's own SDP query) or set `port = 0` and `serviceClassId` to the 128-bit service GUID, in which case "the system attempts to use serviceClassId to resolve the remote port" ("can be used without prior SDP queries"); error table includes WSAEADDRINUSE (channel in use), WSAEHOSTDOWN (RFCOMM DM response), WSAECONNRESET (multiplexor disconnected). Socket is `socket(AF_BTH, SOCK_STREAM, BTHPROTO_RFCOMM)`. — [Bluetooth and connect (Win32)](https://learn.microsoft.com/en-us/windows/win32/bluetooth/bluetooth-and-connect); [SOCKADDR_BTH](https://learn.microsoft.com/en-us/previous-versions/windows/embedded/ee495412(v=winembedded.80))

### Inferences
- The practical cross-platform pattern in 2026 is "portable sans-IO protocol core + three small native transports" (mos9527 libmdr/libmdr-bt, Sony Device Center sony-protocol/sony-transport, overheard mdr-frame/overheard-transport, Nullpoint core/transport-webserial). None of the generic wrappers (32feet, bluetooth_rfcomm, bluetooth-serial-port) is proven on Sony devices, and 32feet/bluetooth_rfcomm both lack reliable SDP on Linux, which matters because the Sony channel number varies per model.
- On Windows, Winsock with `serviceClassId` is the lowest-friction path (no manifest capability, no UI-thread consent prompt); WinRT is only necessary for packaged/UWP distribution.
- On macOS, IOBluetooth's main-run-loop requirement argues for a Swift/ObjC transport layer even if the core is Rust/C++; App Store distribution adds the Bluetooth entitlement and possibly a review-time demand for the network-client entitlement.
- A client should implement SDP-based channel discovery (or OS-level UUID connect) and a connection broker/on-demand release because of the one-connection limit.

### Gaps
- Whether Python's stdlib `socket` supports `AF_BLUETOOTH` RFCOMM on Windows (Fanxingkeming's "zero third-party, Windows `AF_BTH`" claim implies yes in recent Python) was not verified in the Python docs I fetched; the "What's New in 3.14" page was truncated before the socket section.
- No authoritative Apple statement on IOBluetooth RFCOMM under the App Sandbox beyond the generic Bluetooth entitlement; Apple's IOBluetoothRFCOMMChannel page did not render for the fetch tool.
- 32feet's macOS Bluetooth Classic status is unclear (garbled wiki table; open issue requesting a `net-macos` IOBluetooth target).

## Key question 5: Which newer models are reverse-engineered, which are not, and what adding a model involves

### Takeaway
As of 2026-11-06: WH-1000XM5, WF-1000XM5, LinkBuds, LinkBuds S, ULT WEAR (WH-ULT900N) and WH-CH720N are well covered (Gadgetbridge + multiple desktop clients). WH-1000XM6 is covered in most new clients (verified on fw 3.1.5 by hush, Nullpoint, overheard, Sony Device Center; full feature table in mos9527) but only "experimental"/partial in Gadgetbridge and Sony Device Center. WF-1000XM6, LinkBuds Open (WF-L910) and LinkBuds Clip (WF-LC900) appear only in mos9527's device-support docs, Resonance (WF-1000XM6 fully tested) and a few app model lists; LinkBuds Fit (WF-LS910N) and INZONE headsets appear nowhere in the Sony-protocol projects surveyed. Gadgetbridge has no coordinator for WF-1000XM6, LinkBuds Fit/Open/Clip, WH-CH520 or WH-XB910N. Adding a model is mostly declaring capabilities and verifying/probing sub-types and EQ layouts rather than new framing.

### Inferences
- The "long tail" risk is per-model/per-firmware quirks within v2 (XM6's ambient sub-type 0x19, 10-band EQ, table-2 multipoint), not the framing. A new client should budget for a capability-discovery layer plus a built-in frame logger to crowd-source model reports, which is how every surviving project grows its matrix.
- Models not yet in Gadgetbridge (WF-1000XM6, LinkBuds Fit/Open/Clip) are the most valuable targets for a new client, and mos9527/Resonance already show they speak standard v2.

### Gaps
- No project documents LinkBuds Fit (WF-LS910N) or INZONE gaming headsets over the MDR protocol (splitbrain/sony-h5-tray reads only INZONE H5 battery).
- Firmware-version thresholds at which XM6/XM5 behaviour changed (e.g., EQ preset acceptance "as of FW 3.0.0") are documented only anecdotally.

## Key question 6: Legal and licensing considerations noted by these projects

### Takeaway
The ecosystem splits on copyleft: Gadgetbridge (the reference) is AGPL-3.0, so MIT projects explicitly state they read it as a spec but did not copy code; a few derivative projects adopt AGPL "to match Gadgetbridge"; one project (Resonance) relicensed from GPL-3.0 to PolyForm Noncommercial. Every project carries a "not affiliated with or endorsed by Sony" disclaimer and some add trademark notices. ## Key question 7: Does Sony publish an official SDK or developer API for headphone control?

### Takeaway
No. Sony's only public "Audio Control API" (announced December 2017, developer.sony.com) is an HTTP/JSON + SSDP/UPnP API for networked home-audio products (soundbars, AV receivers, wireless speakers); it does not cover Bluetooth headphones. Sound Connect itself is phone-only ("Android smartphones or iPhones only ... not compatible with computers"), and every headphone-control project calls the protocol unpublished.

### Cited Findings
- Sony's Audio Control API launch (Dec 2017) named the STR-DN1080 AV receiver, HT-CT800 soundbar and SRS-ZR5 wireless speaker; "based on well-known protocols; HTTP and JSON", "uses SSDP for device discovery, and DLNA and UPnP". — [App Developer Magazine](https://appdevelopermagazine.com/audio-control-api-announced-by-sony/)
- Home Assistant's Songpal integration describes the same API as covering "soundbars, AV receivers and wireless speakers" with an official list of HT-ST5000, HT-MT500, HT-CT800, SRS-ZR5, STR-DN1080; no headphones. The .NET wrapper `iclanton/SonyAudioControlApi` points to `developer.sony.com/develop/audio-control-api/`. — [Home Assistant Songpal](https://www.home-assistant.io/integrations/songpal/); [SonyAudioControlApi](https://redirect.github.com/iclanton/SonyAudioControlApi)
- Sony's Sound Connect is "for Android smartphones or iPhones only. It is not compatible with computers." — [Android Authority](https://www.androidauthority.com/sony-open-source-headphone-app-3710109/)
- overheard: "The protocol is not published by Sony." Plutoberth: the author "reverse-engineered the application ... defined the protocol, and created an alternative application." — [overheard](https://github.com/andreabedini/overheard); [Plutoberth](https://github.com/Plutoberth/SonyHeadphonesClient)
- The app was renamed: "Sony | Headphones Connect" became "Sony | Sound Connect" in October 2024 (Android package remains `com.sony.songpal.mdr`; APK versions up to 13.0.0 on APKMirror). — [App Store listing](https://apps.apple.com/ua/app/sony-sound-connect/id1168502924?l=uk); [mdr-protocol (package name)](https://github.com/AndreasOlofsson/mdr-protocol); [APKMirror 13.0.0](https://www.apkmirror.com/apk/sony-corporation/sony-headphones-connect/sony-sound-connect-13-0-0-release/)

### Inferences
- Any desktop client must rely on the reverse-engineered MDR protocol; there is no supported path, and Sony firmware updates (e.g., LE Audio expansion on XM6/WF-1000XM5) can change behaviour without notice, which argues for a capability-probing design and an in-app frame logger.

### Gaps
- developer.sony.com could not be fetched directly (blocked for the fetch tool), so the current scope statement of the Audio Control API is sourced from third parties (2017 press, Home Assistant docs, a .NET wrapper) rather than Sony's page.
