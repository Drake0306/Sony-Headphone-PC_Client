# Sony ULT WEAR (WH-ULT900N) — model facts and third-party client support, as of 2026-11-07

Scope note: this researcher covered (a) what the "2026 ULT WEAR" actually is, (b) the headset's protocol, (c) per-project support status with hardware-verified vs README-claimed separation, (d) the ULT-mode wire protocol, (e) feature gaps, (f) public captures/notes. All GitHub facts were pulled through the GitHub API on 2026-11-07; Codeberg facts through the Codeberg API on the same day. Sony's regional support pages (sony.co.in / sony.ca / sony-mea / sony.com.au) returned HTTP 403 to direct fetches, so firmware dates on those pages are cited from search-engine excerpts of the same URLs and cross-checked against the Japanese kunkoku.jp update tracker.

## Key Question 1 — What exactly is the "2026 ULT WEAR" and how does it differ from the 2024 WH-ULT900N?

### Takeaway
There is no distinct 2026 ULT WEAR over-ear. No source — Sony press releases, Sony support/firmware pages, Notebookcheck/What Hi-Fi/SoundGuys/Kotaku coverage through November 2026, GitHub code, or Gadgetbridge — mentions a "ULT WEAR 2", "WH-ULT900N2" or "WH-ULT910N". The only ULT over-ear is the April-2024 WH-ULT900N (FCC codename YY2981), which in 2026 is on clearance and received its last firmware (2.1.0) in December 2025. A developer who "owns a 2026 ULT WEAR" almost certainly owns a WH-ULT900N bought in 2026, most likely on firmware 2.1.0.

### Inferences
- "2026 ULT WEAR" = WH-ULT900N; any client that supports the WH-ULT900N supports it. Firmware differences 2.0.5 → 2.1.0 are security/bugfix only per Sony's notes, so protocol behaviour captured on 2.0.7 and 2.1.0 in 2026 should match.
- LE Audio/LC3 was promised at launch but never appears in Sony's codec page or any firmware note; the fw-2.1.0 support-function list contains no LE-Audio-related function (`0x42 CLASSIC_ONLY_LE_CLASSIC_SETTING` is absent from table 1), so treat LC3 as not delivered. The "LE_ULT WEAR" name is the ordinary BLE GATT advertisement (support functions `0x14 BLE_SETUP`, `0xB2 GATT_CONNECTABLE` are advertised), not LE Audio.
- The device name changed from "Sony ULT" (seen Dec 2024, pre-2.0.7?) to "ULT WEAR" (all 2026 reports); matchers should accept both, which BudsLink, SonyBridge (after PR #26) and Gadgetbridge (after PR #6399) do.

- No primary Sony document states Bluetooth-chip or "V1 processor" details beyond the press-release sentence; chip identity (MT2822M) is from FCC-photo reading, not a lab teardown.
- No evidence either way on whether Sony's Sound Connect app exposes "Find Your Headphones" for this model (it is absent from the help guide and from the owner's 11.1.1 feature inventory).

## Key Question 2 — Which protocol version / service UUID does the ULT WEAR use?

### Takeaway
The WH-ULT900N speaks Sony MDR protocol v2 only, over Bluetooth Classic RFCOMM on the v2 service UUID `956C7B26-D49A-4BA8-B03F-B17D393CB6E2` (SDP record "SPP Serial Port", channel 18 on fw 2.1.0). It reports protocol-info `01 00 03 00 20 02 00 00` (version 0x03002002, table 1 and table 2 enabled). It also exposes the Sony BLE GATT service family (`5b833e06-…`/`5b833e26-…`) but no client uses it. Since the 2026 unit is the same model, the same applies.

### Cited Findings
- "Sony ULT WEAR uses Bluetooth Classic RFCOMM (channel 18) with the Sony V2 protocol (UUID 956C7B26-D49A-4BA8-B03F-B17D393CB6E2)"; init `[0x00,0x00]` → `[0x01,0x00,0x03,…]` "V2 protocol confirmed"; every DATA_MDR must be ACKed with `seq = 1 - received_seq` "or the device endlessly retransmits" — [Leonard013/sony-ult-ctl README](https://github.com/Leonard013/sony-ult-ctl/blob/main/README.md)

Don't hard-code it — it is firmware-specific"; protocol info reply `01 00 03 00 20 02 00 00` → "version 0x03002002, table 1 and table 2 enabled"; model/FW replies `05 01 08 "ULT WEAR"`, `05 02 05 "2.1.0"`; "Only one RFCOMM client at a time … EBUSY" — [owaiskaifi PROTOCOL.md (verified 2026-10-17, fw 2.1.0, Linux/BlueZ)](https://github.com/owaiskaifi/sony-connect/blob/master/docs/PROTOCOL.md)

### Inferences
- A v2-only codebase (libmdr/mos9527, SonyBridge v2 path, sony-device-center V2, Gadgetbridge SonyProtocolImplV2) is the correct base; v1-only or v1-first code (Plutoberth lineage) needs the v2 fallback.
- The absence of `SMART_TALKING_MODE` function IDs in table 1 confirms the help guide: no Speak-to-Chat on this model, so a client should not render that control for it.

### Gaps
- No public SDP dump showing the full record set (only channel 18 and the record name are reported); the channel number is reported for fw 2.1.0 only.

## Key Question 4 — Is the ULT button / bass mode exposed over the protocol? Where is it documented?

### Takeaway
Yes. ULT mode is not a dedicated feature; it is multiplexed into the v2 Equalizer/EBB command family as inquired type `0x03 PRESET_EQ_AND_ULT_MODE` (support function `0x53`). GET `56 03` → RET `57 03 <preset> <ult> <nbands> <band…>`; SET `58 03 <preset> <ult> <nbands> <band…>` → ACK then NTFY `59 03 …`; `<ult>` = 0x00 OFF / 0x01 ULT1 / 0x02 ULT2. Documented in libmdr's generated structs (from Sony's app) and live-verified in sony-ult-ctl, pats01, owaiskaifi and Z-ULT-Connect.

### Cited Findings
- libmdr: `EqUltModeStatus { OFF = 0x00, ULT_1 = 0x01, ULT_2 = 0x02, OUT_OF_RANGE = 0xFF }`; `EqParamUltMode { EqPresetId presetId; EqUltModeStatus eqUltModeStatus; MDRPodArray<UInt8> bandSteps; }` (comment "THMSGV2T1EqParamUltMode", i.e. Sony's own class name); RET/NTFY/SET/capability structs `EqEbbRetParamEqAndUltMode`, `EqEbbNtfyParamEqAndUltMode`, `EqEbbRetCapabilityEqAndUltMode` — [ProtocolV2T1.hpp](https://github.com/mos9527/SonyHeadphonesClient/blob/v1-compat/libmdr/include/mdr/Generated/ProtocolV2T1.hpp)
- sony-ult-ctl: "ULT mode is multiplexed into the Equalizer system — not at a dedicated feature ID"; `SET: [0x58, 0x03, 0x00, ult_mode, 0x06, 0x0A×6]`, `GET: [0x56, 0x03]`, `RET: [0x57, 0x03, eq_preset, ult_mode, 0x06, band1..6]`; 0 OFF, 1 "ULT 1 (bass boost)", 2 "ULT 2 (deep bass)" — [sony-ult-ctl README](https://github.com/Leonard013/sony-ult-ctl/blob/main/README.md)
- owaiskaifi live captures (fw 2.1.0): `57 03 00 02 06 0A 0A 0A 0A 0A 0A` (preset OFF, ULT 2, six flat bands; `0A` = 0 dB centre); SET `58 03 00 01 06 0A×6` → NTFY `59 03 …`; "Do a read-modify-write: echo the preset + bands just read and change only <ult>"; capability `50 03` → `51 03 <bands=06> <steps=15> <ult2AdditionalStep=0A> <npresets=0C> (<id> <name>)…`; `EqPresetId`: `00` OFF, `10` BRIGHT … `17` SPEECH, `A0` CUSTOM, `A1..A5` USER_SETTING1-5; "type 03 is effectively a ULT-only setter, type 00 the full EQ setter" (type 03 ignored preset and bands in a live test); the device answers `56 00` with the same ULT layout; "After `58 03 …` the NTFY comes back as `59 03`, even when the GET used type `00`"; a malformed `58 00 00 00 06` (band count without bands) corrupted the custom EQ to `A0 … 70 3C 00 00 94 44` and reset ULT to off — [owaiskaifi PROTOCOL.md](https://github.com/owaiskaifi/sony-connect/blob/master/docs/PROTOCOL.md)
- Z-ULT-Connect claims the opposite for presets: "EQ presets must be sent through the combined 'EQ + ULT mode' message (`58 03 …`)" — [Z-ULT-Connect README](https://github.com/cristianoashok/Z-ULT-Connect/blob/main/README.md). This conflicts with owaiskaifi's observation that type `03` ignores the preset byte; both are hardware reports on fw 2.1.0.
- pats01 implementation: `set_ult` sends `bytes((0x58, 0x03, 0x00, mode, 0x06, 0x0A, 0x0A, 0x0A, 0x0A, 0x0A, 0x0A))` and parses `57 03` / `59 03` into `ULTStatus(eq_preset, mode, bands)` — [headset.py](https://github.com/pats01/sony-ult-wear-omarchy/blob/main/backend/sony_ult/headset.py)
- Related IDs not advertised by the ULT WEAR (so irrelevant for this model but present in Sony's app): `SoundEffectType::SOUND_EFFECT_ULT/ULT1/ULT2` (EqEbbInquiredType 0x30, support 0x54), `ULT_BTN_SOUND_EFFECT_ASSIGN` 0x40, T2 `SOUNDEFFECT_ULT_BEEP_ONOFF` / BudsLink `VOICE_GUIDANCE_SOUND_EFFECT_ULT_BEEP_ON_OFF: 0x48` — [owaiskaifi PROTOCOL.md](https://github.com/owaiskaifi/sony-connect/blob/master/docs/PROTOCOL.md); [BudsLink sonyConfig.js](https://github.com/maniacx/BudsLink/blob/main/src/lib/devices/sony/sonyConfig.js)
- Help guide confirms the app can set "ULT1/ULT2/OFF" and that the button is "disabled during a call" — [helpguide ULT button](https://helpguide.sony.net/mdr/2981/v1/en/contents/TP1001375636.html)
- Other ULT-WEAR-verified byte contracts from the same sources: NCASM `68 17 <valueChange 00/01> <total 00/01> <mode 00 NC/01 ASM> <asmMode 00 normal/01 voice> <level 00..14>`; "In NC mode the ambient fields are ignored" (set level/voice while in ambient mode); battery `22 00` → `23 00 <level> <charging>` (no threshold byte); volume `A6 20`/`A8 20`/`A9 20` on a 0–30 scale synced with AVRCP absolute volume; multipoint `d6 d1`/`d8 d1 00 XX`+`98 00 06 01` — [owaiskaifi PROTOCOL.md](https://github.com/owaiskaifi/sony-connect/blob/master/docs/PROTOCOL.md); [sony-ult-ctl README](https://github.com/Leonard013/sony-ult-ctl/blob/main/README.md); [SonyBridge MULTIPOINT_RESEARCH.md](https://github.com/AmitRajput-Dev/SonyBridge/blob/main/docs/MULTIPOINT_RESEARCH.md)

### Inferences
- The "6 bands" are Clear Bass + 5 EQ bands (Z-ULT-Connect labels them Bass, 400, 1k, 2.5k, 6.3k, 16k), matching Sony's 5-band+Clear Bass EQ UI for this tier; `steps=0x15` (21) implies −10..+10 around centre 0x0A.
- Safe implementation pattern: always GET `56 03` first, then SET `58 03` echoing preset + bands with only the ULT byte changed; never send a band-count byte without bands. Whether the preset byte is honoured through type `03` is disputed; a client that wants to change presets should test `58 00` (full EQ) vs `58 03` on its own unit.
- The help-guide note that high CLEAR BASS masks ULT2 implies the device applies ULT on top of the EQ chain, consistent with ULT living in the EQ command.

### Gaps
- No capture of the `51 03` capability reply with the preset name list for the ULT WEAR is published verbatim (only its header fields).
- No source documents what the headset does with ULT during a call (help guide says the button is disabled; protocol behaviour of a SET during a call is untested).

## Key Question 5 — Which ULT WEAR features are NOT yet implemented by any client?

### Takeaway
Unimplemented by every third-party desktop client surveyed: Adaptive Sound Control (AUTO_NCASM 0x70), NC/AMB button cycle configuration (desktop; Gadgetbridge has it), Quick Access app assignment (desktop; Gadgetbridge/BudsLink only toggle it), 360 Reality Audio/head-tracking setup, Safe Listening (T2 0x50), voice-assistant selection and voice-guide volume (desktop), Service Link, factory reset (desktop), notification read-aloud/auto-answer (phone-only features), and firmware update. ### Cited Findings
- Device advertises AUTO_NCASM (0x70), QUICK_ACCESS (0xFD) + QUICK_ACCESS_EASY_SETTING (T2 0xF2), VOICE_ASSISTANT_SETTINGS (0xF4), HEAD_TRACKER_ACCEL_TYPE (0xB7), SAFE_LISTENING_HBS_1 (T2 0x50), RESET_SETTINGS (0xF9), GENERAL_SETTING_1/2/3 (0xD1–0xD3), CONNECTION_MODE…LDAC (0xE3), UPSCALING_AUTO_OFF (0xE2) — support-function list [owaiskaifi PROTOCOL.md](https://github.com/owaiskaifi/sony-connect/blob/master/docs/PROTOCOL.md), decoded via [libmdr ProtocolV2.hpp](https://github.com/mos9527/SonyHeadphonesClient/blob/v1-compat/libmdr/include/mdr/Generated/ProtocolV2.hpp)

- Desktop clients with hardware ULT WEAR reports implement only: NC/Ambient/Voice/Off, battery, ULT 0/1/2, (owaiskaifi) volume, (Z-ULT-Connect) EQ presets + custom bands, (pats01) codec switching via PipeWire, (SonyBridge) multipoint on/off + DSEE/EQ inquiries — see Q3 citations.

- Head tracking is consumed only as a sensor stream (OpenTrack/UDP) by sony-head-tracker; no client toggles 360RA/head-tracking settings — [sony-head-tracker README](https://github.com/NicholasSlattery/sony-head-tracker/blob/main/README.md)

### Inferences
- The cheapest high-value additions for a new client on this model: ULT byte in the EQ frame (trivial once EQ is parsed as `EqParamUltMode`), 6-band EQ with presets, auto-power-off (0x25) and pause-on-remove (0xF1) toggles, DSEE auto-off (0xE2), LDAC/connection-quality mode (0xE3), and the Gadgetbridge-proven multipoint toggle.
- Because mos9527's libmdr is generated from Sound Connect and already has the ULT structs, extending it is lower effort than extending SonyBridge/sony-device-center, which hand-code opcodes.

### Gaps
- No public report tests GENERAL_SETTING_1/2/3 (0xD1–0xD3: touch panel, service-link, etc.) bytes on ULT WEAR outside Gadgetbridge's Java; exact payloads are only in Gadgetbridge source (not fetched here).
- Adaptive Sound Control (AUTO_NCASM) wire format for this model is undocumented in every project surveyed.
